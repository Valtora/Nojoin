# Nojoin Architecture Overview

How Nojoin's services, processing pipeline and data fit together. Each section names the code that implements it.

## System at a Glance

Nojoin runs as one Docker Compose stack ([docker-compose.example.yml](../docker-compose.example.yml)). Running it is covered in [DEPLOYMENT.md](DEPLOYMENT.md).

| Service | Role |
| --- | --- |
| `nginx` | TLS proxy. Sends `/api/`, `/mcp` and `/.well-known/oauth-*` to the API and everything else to the frontend. |
| `frontend` | Next.js web client: capture, review, settings and administration. |
| `api` | FastAPI app (`backend/main.py`): REST API, the MCP server mounted at `/mcp` (`backend/mcp_server/`), auth, recording lifecycle and task dispatch. |
| `worker-gpu`, `worker-cpu`, `worker-io`, `worker-parse` | Celery workers, one per lane (below). |
| `db` | PostgreSQL with pgvector. |
| `redis` | Celery broker and result backend, plus short-lived guards and markers. |
| `socket-proxy` | Read-only Docker API, through which the API reads container logs for the admin log viewer. |

| Path | Contents |
| --- | --- |
| `backend/api/v1/endpoints/` | REST routes |
| `backend/worker/tasks/` | Celery tasks, including the `process_recording_task` orchestrator in `pipeline.py` |
| `backend/processing/` | ASR engines, VAD, diarisation, voiceprints, audio analytics, LLM backends |
| `backend/utils/canonical_pipeline/` | Canonical transcript writes, the projection, speaker corrections |
| `backend/services/` | Analytics derivation, exports, calendar sync, CLI OAuth |
| `backend/models/` | SQLModel tables |
| `frontend/src/` | Web client; capture is in `frontend/src/lib/capture/` |

Models: silero VAD; Whisper (default `turbo`), or Parakeet (`parakeet-tdt-0.6b-v3`) or Canary (`nemo-canary-1b-v2`) through onnx-asr; `pyannote/speaker-diarization-community-1` for diarisation; `pyannote/wespeaker-voxceleb-resnet34-LM` for voiceprints; `pyannote/segmentation-3.0` for overlap; `jinaai/jina-embeddings-v2-small-en` for search.

### Worker Lanes

Celery work is split into four queues so a long finalise never blocks light work. Routing is `TASK_ROUTES` in [backend/celery_app.py](../backend/celery_app.py), and an unrouted task falls to the GPU queue. Pool sizes are in [DEPLOYMENT.md](DEPLOYMENT.md).

| Lane | Work |
| --- | --- |
| `gpu` (one slot) | Final processing, live ASR, voiceprint extraction and rebuilds, overlap analytics, model downloads |
| `cpu` | Playback proxies, import audio extraction, delivery analytics, backups, the ffmpeg transcode of non-FLAC segments from older capture builds |
| `io` (also runs Celery Beat) | Meeting Edge, notes and meeting intelligence, speaker inference, chat, AI analysis, transcript indexing, calendar sync, restores, telemetry, cleanup |
| `parse` | Document parsing and RAG index rebuilds |

`worker-parse` runs the `worker-io` image, because visual parsing may go through a subscription CLI that ships only there. It is a separate lane because a document has no page cap and could otherwise hold an IO slot during a live meeting.

The GPU worker keeps the live ASR model loaded while any recording is `UPLOADING`, and otherwise releases model caches after each task. Every task reloads `config.json` first (`task_prerun` in `celery_app.py`), and a settings change applies from the next task without a restart. The API saves the file with a single rename, which keeps a reader from seeing a partial write.

### Runs Lost With A Worker

Celery acknowledges a task when a worker takes it, so a task lost with its worker, as in a restart or a deploy, is never delivered again. Recovery is per kind of work:

- **The pipeline.** When the GPU worker starts, it re-queues `QUEUED` recordings and reclaims each `PROCESSING` one whose `celery_task_id` no worker reports running (`check_queued_recordings` in [backend/worker/tasks/pipeline.py](../backend/worker/tasks/pipeline.py)). Nothing is reclaimed when no worker answers, since a restart of one lane must not steal another's live run. A run that fails before its transcript publishes stays `ERROR`: the transcript it left pending or processing never moves the recording on (`update_recording_status`).
- **Notes, AI analysis and delivery.** Each claims its own status on the transcript row (`notes_status`, `analytics_ai_status`, `analytics_status`) and never changes the recording's status, so a lost run strands only its output. A `generating` claim whose row has gone unwritten for 15 minutes reads as failed, with the message "Generation did not finish. Try again." ([backend/utils/generation_claim.py](../backend/utils/generation_claim.py)): in the 409 that refuses a second run, the recording and analytics payloads, MCP and the recording ETag, so a polling page hears of the expiry. Claiming stamps `updated_at`, the worker stamps it again when it starts, and a heartbeat thread renews it every minute while it waits on the model, so a long meeting in parts on a slow model never reads as lost. While notes generate, reprocessing answers 409.
- **Speaker inference.** **Retry Speaker Inference** holds the finished meeting in `PROCESSING` for its run, with its own task in `celery_task_id`. A finished meeting in `PROCESSING` is recognised by the `processing_completed_at` that only the pipeline clears, or by its step. When an IO worker starts it hands back each hold whose task no worker reports running, to `PROCESSED`, or `ERROR` over a failed transcription. A beat task every five minutes (`release_stale_side_run_holds_task` in [backend/worker/tasks/side_runs.py](../backend/worker/tasks/side_runs.py)) hands back any hold untouched for 15 minutes, which covers a pool child killed mid-run. The GPU worker's sweep hands a hold back too, rather than reprocessing the whole meeting, and a run finishing late leaves a pipeline that started after its hold was released alone.

### Dispatching From The API

`send_task` blocks on Redis, and the API dispatches from `async def` handlers. Request paths therefore dispatch through [backend/core/task_dispatch.py](../backend/core/task_dispatch.py), which publishes off the event loop: `dispatch_task`, or `dispatch_task_best_effort` where a failed dispatch must not fail the request. The API also gives up quickly: connects are capped at 2 s and `apply_api_dispatch_limits` cuts publish and result-backend retries to one, so an unreachable broker costs a dispatch about 6 s. Workers keep Celery's default retries and call `send_task` directly.

When editing `celery_app.py`, note that the broker reads its transport options while the result backend reads top-level `redis_*` keys, and that `send_task` subscribes the result backend before it publishes, so bounding the publish retry alone does nothing.

### AI Providers

LLM backends live in `backend/processing/llm_backends/` (Gemini, OpenAI, Anthropic, Ollama). Each user's AI calls resolve to the install-wide provider (an API key or Ollama) or **CLI OAuth**, which runs the user's own Claude subscription through the Claude Agent SDK, or ChatGPT subscription through the OpenAI Codex CLI, on the IO lane. CLI OAuth falls back through the server's provider chain on any failure, and no feature may depend on it; [SECURITY.md](SECURITY.md) covers the trust boundary.

An install-wide secondary provider (`secondary_llm_provider`, or `SECONDARY_LLM_PROVIDER`) wraps the primary in `SecondaryLLMBackend`. Any primary failure is retried on the secondary, which has its own models and key, and if both fail the primary's error is raised. A streamed answer falls back only when the primary failed before its first token.

### Document Parsing

`process_document_task` (parse lane, `backend/processing/documents/`) writes one `document_pages` row per page, slide, sheet or heading-bounded section, and records which tier produced each:

1. **Structural.** For PDFs, pypdfium2 text in the order the file draws it, which keeps columns apart, and pdfplumber tables found from their ruling lines; for Office files, the underlying XML, which yields slide titles, table cells, speaker notes and the values behind native charts.
2. **Visual analysis** (on by default) sends each page's images to the user's model. For PDFs and images the model sees the rendered page and its output replaces the text layer; for Office files it sees the embedded figures and its output supplements the structural text. The model gets a copy of each image fitted to every provider's limits ([vision_input.py](../backend/processing/documents/vision_input.py)): at most 2,576 px on the long edge and 3.5 MB of file, upright by its EXIF orientation, with transparency laid over white. A small PNG or JPEG goes as it is; anything else is re-encoded as PNG while that fits, else as JPEG. A picture Pillow cannot open, such as an EMF or WMF drawing, is left out rather than sent, and the document's warning counts it. A page's pictures go in order, as many to a call as fit in 8 pictures and 14 MB of file: about 18.7 MB once base64-encoded, under Gemini's 20 MB of inline data a request (the Claude API takes 32 MB), and few enough to describe within the call's 8,192 output tokens. The answers are joined in picture order. The stored file is never changed, and OCR reads it.
3. **Local OCR** (Tesseract, in the worker image) supplements pages with little text layer, and needs no AI provider.

Pages are written as they complete, so a restarted worker resumes at the first missing page. A provider that cannot take images raises `VisionUnsupportedError`, which drops the whole document to a structural parse with a warning; for an image upload, which has no text layer, it is an error. Any other failed vision call costs only its own pictures. A page another call described keeps that text, and a page whose every call failed falls back to OCR or its structural text. The document's warning counts those pages and pictures; the provider's error goes to the worker log.

Pages feed the search index (`context_chunks`, one chunk per page unless a page exceeds the embedding window), the notes prompt and the MCP `get_documents` tool. Document text is untrusted, and a vision model reproduces any instruction printed on a page, so the notes and chat prompts wrap it in `<attached_document>` tags with an instruction to treat it as data.

Each document's original file is stored flat in the documents directory under a name of its own (`<uuid>.<ext>`, or `<stem>__<uuid><ext>` when a restore finds the name taken), so no two rows share a file. The rules live in [backend/utils/document_storage.py](../backend/utils/document_storage.py):

- **Deletion.** Deleting a document removes its file, and so does every path that deletes a recording: delete, permanent and batch permanent delete, discard, deleting a user, and a restore in **Overwrite** mode (**Clear all existing data** empties the directory). Under **Overwrite**, a restored document that takes the name of the copy it replaced keeps that file: the restore unlinks before it moves files in, and skips any file a row still names, compared by device and inode so another spelling of it counts. The staged file of a restored row that fails to insert goes with the staging directory.
- **After the commit.** Files are unlinked only after the delete commits, so a failed commit never leaves a row without its file. A failed cleanup is logged and never turns the committed delete into an error. A cancelled unlink still runs, on the event loop, because it is the only thing that would remove the file.
- **Uploads racing a delete.** Deletes lock their recordings `FOR UPDATE` before reading the document paths. A document insert waits on the same lock, so an upload cannot commit a row the delete never read. The API's deletes take the locks in id order, and deleting a user locks the user row first. A restore in **Overwrite** mode does not: it locks the recordings it replaces before the user rows it inserts against, and locks one its pre-delete missed only on reaching it. A user deletion running alongside can then deadlock with it, and PostgreSQL aborts one of the two, which rolls back with no file removed. An upload writes its file before its row and removes it if the insert fails or is cancelled; an insert that lost the race answers 404.
- **Containment.** Only paths inside the documents directory are unlinked. A legacy row pointing elsewhere keeps its file, and the path is logged.
- **Parses.** A parse whose document is deleted stops at its next write. One that fails on a write is still marked `ERROR`, with a fixed message; the database's text goes only to the log.
- **Sweep.** A file left without a row, as by a process that dies between a commit and its unlink, is reported daily and removed only when configured ([Storage Hygiene](#storage-hygiene)).

### Meeting Analytics

Analytics come in four tiers. The evidence behind each design choice is in [ANALYTICS_EVIDENCE.md](ANALYTICS_EVIDENCE.md), and the read that assembles them is `read_recording_analytics` in `routes_analytics.py`.

During capture and processing, `GET /transcripts/{recording_id}/analytics/live` is a separate, ownership-scoped, read-only contract. It reads canonical utterances first, with the transcript projection as fallback, and resolves current live speaker names. A pending `UNKNOWN` line counts under the speaker of the line before it when both carry the same audio source, as the transcript shows it. Its typed public response reports provisional talk time, shares, turn structure and transcript-derived words per minute. Talk and turn calculations reuse the deterministic analytics functions; pace uses the delivery constants, per-utterance rate and median, excluding short and overlapping samples and withholding a rate below the minimum sample count. It carries no measured-delivery field, silence estimate, audio overlap or AI result. The read performs no canonical backfill, audio measurement, task dispatch or AI-budget claim, and needs no migration. The final analytics GET and both generation routes refuse in-flight recordings before any final work can start.

The recording view polls this live contract every three seconds only while Analytics is open, ignores a response that lands after completion or a recording change, and switches to the final contract on completion. Analytics playback uses the recording view's shared playback capability. Silence, Talked over, audio delivery, pitch and AI analysis remain labelled after processing.

| Tier | Source | Stored | Code |
| --- | --- | --- | --- |
| Speaking dynamics | `transcript_utterances`, derived on every read | No | `backend/services/meeting_analytics/` |
| Delivery | The audio, CPU lane | `analytics_payload.delivery` | `backend/processing/delivery_descriptors.py` |
| Overlap | The audio, GPU lane | `analytics_payload.audio_overlap` | `backend/processing/audio_overlap.py`, `backend/worker/tasks/analytics_overlap.py` |
| AI analysis | A model reading the transcript, IO lane | `analytics_payload.ai` | `backend/utils/meeting_analysis/`, `backend/worker/tasks/analytics_ai.py` |

The three stored tiers write one JSONB column from three lanes, so each merges its own top-level key under a row lock through `backend/utils/analytics_payload.py`.

Speaking dynamics (talk-time share, turn structure, response latency, a talk-share timeline, silence and overlap totals) are derived on read: every recording has them without a backfill, and a speaker merge, rename or transcript edit shows on the next read. Figures group by `recording_speaker_id`, which a merge redirects. The package has no ORM or ML imports below its query layer, and its thresholds are in `constants.py`. Rules every consumer relies on:

- Per-speaker talk time counts overlapping speech once for each speaker, so shares are reported against total speech, and both denominators are carried.
- Anything excluded from a statistic is counted.
- Finalised `UNKNOWN` lines, which the transcript view hides once any line has a speaker, are left out of every speaker figure, transition and warning, and counted under `metrics.unattributed`. Delivery and AI analysis read the same lines through `split_analysed_utterances`.
- There are no interruption counts. The merge gives each segment one speaker from a mixed stream, so a transcript holds no overlapping speech. Overlap is measured from the audio and never attributed to a person.
- Gaps at speaker changes are reported in three counted parts: immediate handovers (under the 250 ms collar, `LATENCY_COLLAR_MS`), a reply-time median over gaps from the collar to 5 s, and lapses of 5 s or more.
- A structured warning flags doubtful speaker attribution with reason codes (`low_share_clusters`, `speaker_cap_bound`, `unnamed_speakers`). The web client owns the wording and shows nothing for a code it does not know.

#### Delivery Descriptors

Speaking pace, pitch height and movement (YIN, spread in semitones), loudness and within-turn pausing. No emotion model is used, and none should be added. The module uses numpy and soundfile only and never imports torch. A file soundfile cannot open (WebM/Opus or MP4/AAC from captures made before FLAC capture; M4A, AAC, MP4 or WMA imports) is first decoded with ffmpeg to a temporary 16 kHz WAV that keeps its channels.

`compute_delivery_analytics_task` runs on the CPU lane as a post-processing follow-up, and from the Analytics tab's **Measure delivery** action for older recordings. In a browser capture, channel 0 is shared audio and channel 1 the microphone, so each utterance's dominant channel, judged with the live lane's thresholds, identifies its source; an imported stereo file is downmixed. Loudness is compared across speakers only when they shared a signal chain.

The payload carries `DELIVERY_METHOD_VERSION` and the transcript event watermark it was measured at. Stale figures are re-measured when the Analytics tab is next read, if the owner's `auto_remeasure_delivery` setting is on (the default), with a five-minute per-recording claim so the tab's polling cannot queue the run twice. A measurement that ended in error is never retried by a read. After a method-version bump, `remeasure_outdated_delivery_task` re-measures up to 25 recordings every six hours.

Cross-meeting baselines compare a speaker linked to a person with that person's medians over the user's other measured meetings. They are derived on read, use the same method version only, and need three such meetings (`BASELINE_MIN_MEETINGS`). The wording describes delivery, never emotional state.

#### Measured Overlap

`compute_overlap_analytics_task` runs `pyannote/segmentation-3.0` on the GPU lane. `backend/processing/segmentation_model.py` loads the model, and overlap is its only use. It is dispatched with the other follow-ups, and by **Measure delivery** for older recordings. Audio soundfile cannot open is decoded to a temporary 16 kHz mono WAV first. The result has its own method version and status under `audio_overlap` and needs no staleness check, since the audio does not change after processing.

It reports that people talked over each other, for at least how long, and where. It never says who overlapped whom, and the interface presents the total as a floor because the detector underestimates.

#### AI Analysis

A model reports the topics and who drove each, how each speaker's words read, which questions were asked and which went unanswered, and who proposed, agreed with or objected to each decision. The tier has its own `analytics_ai_status` column, which adds `unavailable` (no AI provider, a normal state) and keeps an AI failure from marking delivery as broken.

It runs on request, from the Analytics tab or the MCP `analyse_meeting` tool. An administrator may cap runs per user per UTC day (`ai_analysis_daily_limit` in `config.json`, overridable on the user record). Runs are logged in `ai_analysis_runs` when queued, a run past the cap gets 429, and the read reports the remaining budget. A user may opt in to running it after every processed meeting (`auto_analyse_meetings`, off by default), within the same budget.

The parser, not the prompt, enforces three rules:

- Speakers are an allowlist of the meeting's display names. Anything attributed to another name is discarded.
- A citation must appear in the transcript that was sent (normalised for case and punctuation, matched across turn boundaries) and its timestamp must fall inside the meeting. A sentiment or decision item left with no valid citation is dropped.
- Every discard is counted.

Sentiment is read from the words alone and never combined with delivery. The tier answers who drove topics and decisions; the decision log stays in the notes. Consensus is `stated`, `assumed` (the decision went unchallenged, which the interface must not show as agreement) or `none`. A very long meeting is truncated and the payload records how far the analysis reached. The payload carries a method version and transcript watermark, and when stale the tab offers to regenerate instead of calling the model again unasked.

### Exports

`GET /api/v1/transcripts/{id}/export` builds a PDF, DOCX or plain-text file from any of the notes, analytics and transcript (`backend/services/exports/`):

- `builder.py` turns a meeting into an `ExportDocument` of neutral blocks. Notes are parsed from Markdown with `markdown-it-py`. Analytics come from `read_recording_analytics`, the Analytics tab's own read, so an export cannot show different figures and never dispatches a measurement. The wording ports the tab's components (`formatDuration.ts`, `deliveryInsights.ts`, `AttributionWarning.tsx` and the AI panels), with tests that pin the parity.
- The transcript section places the user's timeline notes with `place_timeline_notes` on the lines it prints and interleaves them with `iter_timeline`. Each note is a quoted paragraph (`> ` on every line in plain text); a note at a time is one line, stamped like the transcript's, so its text cannot pass for a line of speech.
- A note's file follows its note (`MeetingParts.note_files`, from `load_recording_timeline_notes_async(..., with_files=True)`). An image becomes an `ImageBlock`: the picture scaled to at most 1,600 px (`render_for_export` in `backend/utils/note_attachments.py`) under the note's own line, kept on one page, in PDF and DOCX. Plain text, and any other file, add a line `Attached: <name>` to the note. `include_notes=false` leaves the files out with their notes.
- A request with `include_notes=false` leaves the user's notes out of the whole file: the transcript's timeline notes, and the `## User Notes` section that ends generated notes, which the notes section cuts with `split_user_notes_section` (`MeetingParts.include_user_notes`). The stored notes are not changed.
- One renderer per format draws the blocks: ReportLab for PDF, python-docx for Word, and plain text. `charts.py` lays charts out once, painted as vectors in the PDF and as a PNG in Word. Rendering runs in a threadpool, off the event loop.
- Automatic speaker colours exist only in the browser, so the export dialog sends the colour map it shows; `speaker_colors.py` falls back to saved colours, then chart slots.
- The DOCX embeds Geist Regular and Bold as obfuscated font parts so Word does not substitute them. The fonts and their licence are in `backend/services/exports/assets/fonts/`.
- A Word document is XML, which cannot hold the C0 control characters other than tab, newline and carriage return, a lone surrogate, U+FFFE or U+FFFF, and python-docx refuses any string with one. `render_docx` drops them from the whole document before it writes anything. Pillow, which paints the DOCX charts, fails on a paragraph separator such as a carriage return, so a chart label draws one as a space. PDF and plain text keep these characters.

### Web Client

The Next.js app in `frontend/` covers the dashboard, recordings and transcript review, analytics, speakers, notes, chat, documents, and user, admin and system settings. It is the only capture surface; a browser that cannot capture keeps everything else.

#### Connectivity Monitor

`frontend/src/lib/connectivity/` decides when the API is unreachable and is built to avoid false alarms. Any success (API traffic, a health poll or an idle probe) proves the backend is up, so a busy page never probes. Only the prober can declare an outage, once the last success is 30 s old and three probes in a row have failed. Probes are serialised, so a burst of failing requests cannot reach the threshold at once. A probe that overran its timeout by a wide margin is discarded, because a frozen tab suspends the timer and the request together, and returning to the foreground clears the failure streak. The monitor relies on elapsed wall-clock time because the `resume` event is not dispatched on every Chromium build. A false outage would also mislabel a capture shortfall as `backend-unreachable` (below).

### Browser Capture Stack

Capture lives in `frontend/src/lib/capture/`. Browser support and troubleshooting are in [CAPTURE.md](CAPTURE.md).

- **Sources.** On desktop the browser asks for shared tab, window or screen audio and the microphone and mixes them with Web Audio. Mobile Chrome records the microphone alone, leaving the shared channel silent.
- **Segments.** An AudioWorklet tap (`frontend/public/audio-worklets/pcm-tap.js`) feeds the two-channel mix to `frontend/src/lib/capture/pcm/`, which resamples it to 16 kHz with a windowed-sinc filter, cuts exactly 32,000 frames (2 s) per segment by counting samples, and encodes each as FLAC. Nothing restarts between segments, so they join with no gap. Channel 0 is shared audio and channel 1 the microphone.
- **Upload.** Segments upload one at a time, in order, with the session cookie. Each is written to IndexedDB when recorded and removed when the server acknowledges it, so a closed tab keeps what it had not sent, and the next resume or stop in that browser sends it first.
- **Unload.** A real tab unload (`pagehide` or `beforeunload`) drops the unfinished segment and pauses the recording with a beacon. In-app navigation and switching tabs do not. A paused recording must be resumed, stopped or discarded before another capture starts; stopping needs no live browser runtime.
- **Interrupted capture.** A beacon refused while signed out, or lost to an outage, leaves the recording `UPLOADING` with no tab capturing it. The recording payload's `capture_stalled` is true once a live capture (`client_status` `RECORDING`) has gone two minutes without an upload, start or resume (`capture_looks_stalled`, judged on the server's clock). The client lists the user's `PAUSED` and `UPLOADING` recordings. A paused one, or a stalled one, needs a decision unless a tab of this browser holds its Web Lock (`frontend/src/lib/capture/captureLock.ts`), which the capturing tab takes in shared mode for as long as its capture runs and the browser drops when the tab goes. Passive checks only badge such a recording. The resume-or-discard dialog opens when the user opens it, selects **Start Meeting** or selects **Import Audio**. **Start Meeting** looks only once `POST /api/v1/recordings/init` refuses it with `active_recording_exists`, so the share picker, which needs the click's user activation, follows a single request. While the user has an unfinished capture and this tab runs none, the client looks again every 30 s while the tab is visible, and once when a hidden tab shows again. Resume accepts a stalled capture as if paused and refuses one still uploading, unless the request carries the current capture epoch as the tab holding the capture, or as `reclaim_epoch` from that tab after a reload ([Capture Epochs](#capture-epochs)). Nothing pauses or finalizes a capture automatically, since the server cannot tell a closed tab from one that is cut off.
- **Recording header.** The header's capture slot (`frontend/src/components/RecordingCaptureSlot.tsx`) gives the transport only to a tab whose stored capture is that recording and that either holds it in its runtime (`ownedRecordingId`, a failed stop's retained runtime included) or holds the current recovery offer for it (`pausedRecording`), as a tab reloaded during the capture does: the same test the live controls apply to Stop and Discard. Such a tab has no runtime, so the header's Resume goes through the recovery dialog's own handler (`useResumeRecoveryOffer`), which shares again and reclaims the capture with the stored epoch; without an offer, Resume needs the tab's live tracks. The page itself keeps a recording in flight ahead of the server's status, without playback or export, only while this tab's runtime holds it (`localCaptureActive` in `useRecordingDetail.ts`), so a recording finished on another device after a reload plays here at once. The stored recording ID alone is not ownership, since another tab or device may have taken the capture over. Every other tab shows the server's state, Live or Paused, and the page's audio clock (`frontend/src/lib/notes/audioClock.ts`), since `duration_seconds` stays 0 until finalize.
- **Pause.** The recorder pauses and the tab reads paused at once. The controller then sends the queue and pauses the recording on the server, owing the pause as after an upload stall (below) when the request does not arrive. A pause the server refuses leaves the tab paused with the server's error, and is not sent again.
- **Stop.** Stop releases the microphone and shared tab as soon as the recorder has stopped, then sends the queue and finalises. Every stage is bounded and reports its stage, so a stalled recorder or uploader ends in a retryable finalise. The one unbounded wait is for the user to sign back in, below.
- **Upload stall.** A segment that fails six times in a row (about 15 s) stalls the uploader, which keeps its queue, and the controller pauses the recorder and then the recording. The tab reads paused and keeps its runtime and Web Lock whether or not that pause reaches the server. A failed stop, which leaves the server holding the capture as uploading, and a pause from the controls whose request does not arrive, owe the server a pause in the same way. An unacknowledged pause is sent again once the connectivity monitor records an answer from the API newer than the last failed attempt, after the queue drains, and before any resume, so it cannot land after one. The first retry goes on the first such answer. After two or more failures in a row the next waits 2 s, doubling to 30 s, since a pause that alone keeps failing while the API answers everything else would otherwise go again on every connectivity probe (issue #599). A resume sends it at once. It carries the tab's capture epoch, so once another tab or device has taken the capture over it is refused instead of pausing the capture there ([Capture Epochs](#capture-epochs)).
- **Session expiry.** While a capture runs, or a stop is still sending audio, the controller holds sign-in in place through `frontend/src/lib/session.ts`. A 401, or a 403 for a pending password change, then leaves the page where it is instead of reloading to `/login`, which would end the capture. Uploads and the pause, resume and finalise calls wait for the user to sign back in rather than counting as failures, and a dialog signs in through `POST /login/session`. The hold is pinned to the account that was signed in when it began: a sign-in as anyone else, including one made in another tab, which shares the cookie, ends the session for the capture instead of resuming it. Each request is stamped with the sign-in it was sent under, so a 401 that arrives after the user has signed back in changes nothing. Notes not saved yet hold sign-in the same way, with or without a capture ([Timeline Notes](#timeline-notes)). For the same reason, the recording page treats a 404 for its recording, from a poll or a reload of the view, as a removal only once `/users/me` names the account that first loaded the recording (`useRecordingNotFound.ts`), and leaves once a second request confirms the 404. Under another account's cookie it stays. Where sign-in is held, the answer goes to `noteSignedIn`, which opens the held dialog for the owner; otherwise the page says so once, and the check tells neither the session nor the notes store (`getUserMe`), so the tab's session, its notes persistence and any later hold stay the owner's. While the 404s go on, it asks again at most once a minute per tab. A page that never learnt its account claims no removal.
- **Page updates.** `CaptureProvider` hands `useCapture()` consumers a new state only when the capture itself changes: its status, ownership, recovery offers, settings, stop stage or coverage warning. The fields that change many times a second, the meter levels on every animation frame, the elapsed time every second and the upload queue and sequence on every segment, are read with `useCaptureState(select)`, which re-renders only the component that reads them, and the waveform draws each level sample on its bars without a render. Until issue #822 every sample re-rendered every consumer, the recording page and the recordings rail among them, and that stream of urgent renders kept a navigation's transition from finishing for tens of seconds while a capture ran.
- **Wake lock.** A screen wake lock is held while capturing and re-taken on each return to the foreground. This prevents device sleep only; nothing in a page can stop the browser suspending a tab (see [CAPTURE.md](CAPTURE.md#chrome-memory-saver)).
- **Coverage.** A suspended tab stops recording without raising an error, so the client compares the server's `captured_audio_seconds` (on the recording detail payload, polled every 15 s) with elapsed recording time. The shortfall excludes audio still queued for upload, which is shown separately, and a queue over 30 s also shows on the recording controls. The warning names a cause: `backend-unreachable` when the monitor reports the API down, or did in the last five minutes (queued audio will upload on reconnect); `tab-suspended` when the page was seen to thaw or the recorder watchdog caught a stall (the audio is lost; this outranks an outage); otherwise `unknown`. Once dismissed, it returns only if the shortfall grows materially.

## Recording Flow

A recording moves through `UPLOADING` (capturing) and `PAUSED`, then `QUEUED`, `PROCESSING`, and `PROCESSED` or `ERROR`.

1. **Start Meeting** calls `POST /api/v1/recordings/init`, which creates an `UPLOADING` recording owned by the user and returns its capture epoch ([Capture Epochs](#capture-epochs)). Init, segment, pause, resume, discard and finalise all use the browser session.
2. The browser uploads each segment to `/recordings/{id}/segment?sequence=N&epoch=E`, numbering from 0.
3. The API decodes each FLAC segment to a 16 kHz, two-channel WAV, registers it (see [Chunk Registration](#chunk-registration)) and dispatches the live lane. A segment that is not 16 kHz, two-channel, 16-bit FLAC, or will not decode, is quarantined as a `.corrupt` tombstone and the upload still succeeds, costing a 2 s gap. WebM, Ogg and MP4 segments from tabs on an older build go to the CPU lane for an ffmpeg transcode first.
4. `POST /recordings/{id}/finalize` accepts an `UPLOADING` or `PAUSED` recording, so a capture whose browser is gone can still be processed. Missing sequences and pending transcodes get a retryable 409. Otherwise it rebuilds chunk offsets and window manifests from the segments on disk, seals the cursor, joins the segment WAVs into a FLAC master with soundfile, takes the duration from the frames written, and queues `process_recording_task` and `generate_proxy_task`. The browser sends its elapsed recording time, which the `capture_coverage` pipeline metric compares with the stored audio.

A recording can be discarded while uploading, paused, queued or processing. Discard revokes the running task with `terminate=True` and removes the recording's row, so a requeued task finds nothing to process. Once that delete has committed it removes the recording's files: its audio, its segments and its documents. Finished recordings go through the normal delete. Finished means processed once, not the current status: notes generation, speaker inference and a reprocess show a finished meeting as queued or processing. `Recording.first_processed_at` is stamped on the first flush that makes a recording `PROCESSED` (a mapper event, so every writer does it) and never cleared, a restored recording gets one, and while it is set discard answers 409 (`recording_is_discardable`, which the payload's `discardable` reports). Speaker inference likewise runs only on a `PROCESSED` recording, and its task hands back only a recording still `PROCESSING`, so neither can end a live capture before its audio is assembled. Reprocessing refuses a paused capture (409) as well as one still uploading, and notes generation refuses a live or paused capture (`is_live_capture`, 409), since its run would mark the recording `PROCESSING` and refuse the capture's next segment. MCP's `reprocess_recording` and `regenerate_notes` call the same routes, and every MCP tool gives the assistant a route's refusal as its reason (`logged_tool`).

### Chunk Registration

Each Resume stores the sequence after the highest segment the server holds in `Transcript.settling_state.resume_chunk_sequences`, under the capture publication fence. If the tab still holds audio recorded before the pause (after an upload stall, a pause sent while offline, a failed Stop, or a reload with unsent audio), that audio uploads after the Resume, and the break lands where it starts rather than where recording resumed. Once chunks are placed, their cumulative offsets locate that sequence on the recording's audio timeline. Live word projection and whole-line audio segmentation break there. Live segments and utterance deltas carry an optional `capture_interval` ordinal after a resume; absent means the initial interval. Pending-speaker presentation and overlap grouping cannot join different intervals. Finalise retains the reconciled offsets as `resume_boundaries_ms`, so final line building and reprocessing keep those breaks after temporary chunks are removed. Consolidation and short-line folding cannot join across a resume. These capture markers do not enable word settling and need no schema migration. A final ASR segment with no usable word timings is kept intact if it straddles a boundary, since its wording cannot be split accurately.

Each segment becomes a `recording_audio_chunks` row with an offset on the recording timeline, and each 20 s window (5 s hop) a `recording_audio_window_manifests` row on which the live lane tracks ASR progress. `backend/utils/recording_audio_registration.py` registers a segment in constant time:

- A per-recording cursor (`recording_audio_chunk_cursors`) records how far chunks are placed. A chunk is placed once every earlier sequence is placed or has failed for good (a `.transcode_failed` marker or a `.corrupt` tombstone); a segment that arrives early waits until the gap fills.
- Offsets are cumulative over the chunks present, and a missing sequence ends a contiguous group of windows. Placing chunks can only grow the last group, so registration rebuilds windows from the first one that was not yet full, writes only new or changed ones, and leaves the status of the rest alone. The result matches a full rebuild.
- Registration is serialised per recording with `pg_advisory_xact_lock`, so it never locks the `recordings` row. The upload writes `last_activity_at` at most every 15 s.
- The live lane's text write for each run takes the same lock and then the Transcript fence, the order Stop uses, once its transcription has finished and before it adds lines or updates window manifests. Finalise holds both to its commit, so a live write that arrives during a stop waits, then finds the recording queued and writes nothing. Live labels, settling and naming take only the fence, never this lock, so the order has no cycle.
- Finalise runs the full rebuild as reconciliation and then seals the cursor. A sealed cursor makes registration a no-op, so a transcode task still queued at stop cannot reopen sealed windows. A resume after a failed stop drops the seal and rebuilds the cursor from the chunk rows, as happens for a recording that was in flight across an upgrade.

### Capture Epochs

`recordings.capture_epoch` names the tab holding a live capture, so a tab whose capture was resumed elsewhere cannot overwrite the segments recorded since (issue #570). Segments are numbered by the browser and stored as `<sequence>.flac`, so without it two tabs writing the same sequence replace each other's file and chunk row.

- **Issue.** Init starts the epoch at 0. A resume without an `epoch` takes the capture over and issues the next one. A resume with the current epoch is the holding tab carrying on: it leaves the epoch as it is and is accepted whether the server holds the capture paused or still uploading, since no other tab or device can be running it. A tab that unloads mid-capture keeps its epoch in `sessionStorage` (`PausedCaptureContext.epoch`). After a reload, the capture is offered to it at once while the recording payload's `capture_epoch` is still that epoch and no other tab of this browser holds its Web Lock, and its resume sends that epoch as `reclaim_epoch`: a capture still uploading under it is taken over without waiting to stall, and issued the next epoch, so the old page's late beacon or segment is refused (issue #778). Any other `reclaim_epoch` leaves the usual rule in place.
- **Fence.** Segment, pause, finalize and discard requests carry the sender's epoch, and one from an earlier epoch is refused with a 409 whose detail code is `capture_superseded`, as is the old tab's own resume. A request without an epoch is not checked: tabs on an older build send none, and a stop or discard from a dialog or the recordings list acts for no tab.
- **Ordering.** A segment streams to an `.upload-tmp` name and is given its sequence number only after the epoch check, under the recording's audio advisory lock (`_lock_capture` in `backend/api/v1/endpoints/recordings/capture_audio.py`). Resume issues an epoch under the same lock, and finalize holds it from its first read to its commit. A segment from the old epoch therefore lands before a takeover reads the last sequence, and the new tab numbers after it, or it is refused; and no resume can take a capture over while its master is built.
- **The old tab.** A refused request makes the tab stop its recorder, release its media, Web Lock and uploader, and read idle with the message that the recording continued elsewhere. Its unsent segments are kept to download (Left-out audio, below).
- **A capture discarded elsewhere.** Discard deletes the row, so the old tab's requests answer 404. So does a request sent under another account's sign-in, which a sign-in in another tab causes by replacing the shared cookie. The controller therefore stands down on a 404 only once `/users/me` names the account the capture belongs to (`ownerId`, taken when it starts) and the recording still answers 404 to a second request (`captureGoneError` in `frontend/src/lib/capture/controller.ts`). Under another account, a tab holding sign-in passes the answer to `noteSignedIn`, which opens its dialog, and the request waits for the owner (issue #602). A discard that finds the recording already gone succeeds.
- **A capture stopped elsewhere.** A stop from a dialog finalizes without an epoch and issues none, so the tab that held the capture still holds the current epoch. Its requests are refused instead by the recording's status, with a 409 whose detail is `Recording is no longer accepting capture uploads`, and the tab stands down in the same way on the first one, saying the recording was already stopped. Discard accepts a queued or processing recording, so a discard that carries an epoch is refused with that 409 too once the recording is neither `UPLOADING` nor `PAUSED` (issue #590).
- **Kept audio.** Each stored segment records the epoch it is queued under, and a runtime that adopts kept segments stores them again under its own. A takeover in the same browser sends them only when they were kept under the epoch just before it, and a stop with no live capture sends only those kept under the epoch the server holds, under that epoch. Anything else was recorded before someone else carried the capture on, would land out of order, and leaves the queue to be kept to download, as does any audio past a gap in the queue.
- **Finished elsewhere.** Kept audio is sent only when this browser resumes or stops its capture, so audio kept for a capture stopped, discarded or taken over and finished on another device would otherwise stay. Each time the client lists the user's unfinished captures it looks up every other recording the store holds audio for. It keeps that audio to download when the server reports the recording finished, and removes it when the server answers 404 while `/users/me` names the account recorded with the audio (`ownerId` on each stored segment), since the recording was discarded. Another account gets the same 404 for a recording it does not own, so a 404 for audio with no owner or another owner keeps it, and the page does not ask about it again (issue #589).
- **Left-out audio.** Audio that can never join its recording, as above, is joined in the browser into one FLAC file (`joinFlacSegments` in `frontend/src/lib/capture/pcm/flacJoin.ts`) and kept in an IndexedDB database of its own, `nojoin-left-out-audio`, with the id of the account it was recorded under (issue #605). Each segment is a FLAC stream that numbers its frames from 0 and ends on a short block, so the joiner rewrites every frame header as a variable-blocksize frame numbered by sample, recomputes both CRCs and copies the subframes unchanged; a backend test reads a joined fixture with libFLAC. `frontend/src/lib/capture/leftOutAudio.ts` offers each file in a persistent notification to the signed-in account that owns it, again on every page load until it is downloaded or deleted, and removes any more than seven days old, whoever owns it. The audio stays out of `nojoin-capture` because a new store there needs a version upgrade, which any tab still open on an older build would block.

## Processing Pipeline

`process_recording_task` ([backend/worker/tasks/pipeline.py](../backend/worker/tasks/pipeline.py)) runs on the GPU lane:

1. **Resolve audio.** Validate the source, restoring it from the proxy if needed.
2. **VAD** ([backend/worker/tasks/vad_stage.py](../backend/worker/tasks/vad_stage.py)). Resample to 16 kHz mono and mute non-speech with silero VAD (`enable_vad`). Under 1 s of speech completes the recording with an empty transcript. Each later stage then reads either the muted file or the unmuted one, and muted transcription may read a third file, opened inside every diarised turn (see [Muted Audio Per Stage](#muted-audio-per-stage)).
3. **Diarisation** starts with pyannote community-1 (`enable_diarization`), on the unmuted file unless `vad_mute_diarization` is set, bounded by the recording's `max_speakers` when set. The [final speaker pass](#final-speaker-pass) can augment its turns with offline Nemotron. Phantom speaker filtering then takes clusters within `phantom_max_duration_s` and `phantom_max_segments`: one below `phantom_embedding_floor` against every main speaker is treated as noise and reassigned, one above `phantom_merge_threshold` merges into the speaker it matches, and one in between is kept. The turns of a cluster treated as noise stay muted for transcription. A diarisation that fails leaves one speaker, and transcription still runs.
4. **Transcription** through an engine in [backend/processing/engines/](../backend/processing/engines/) (see [ASR Engines](#asr-engines)), less the words it placed in digital silence (see [Words In Digital Silence](#words-in-digital-silence)). It runs after diarisation so that muted transcription can hear the speech diarisation found (see [Muted Audio Per Stage](#muted-audio-per-stage)).
5. **Merge and consolidation** (see [Word Timestamps In The Merge](#word-timestamps-in-the-merge)).
6. **Speaker assignment.** Voiceprint extraction, names carried from earlier naming acts, identification against the People library, and the duplicate-merge pass (see [Speakers And Voiceprints](#speakers-and-voiceprints) and [Speaker Names](#speaker-names)).
7. **Canonical finalise**, when `enable_canonical_transcript_writes` is on (the default). `finalize_utterances_from_segments` in [backend/utils/canonical_pipeline/core.py](../backend/utils/canonical_pipeline/core.py) writes the merged segments as finalised utterances, supersedes every other active utterance (the live lane's included) while keeping the user's locked text and speakers on lines it matches, and rebuilds the transcript projection. This is committed before step 8, so a later failure cannot undo it. With the setting off, the segments stay in the transcript's JSON only.
8. **Meeting intelligence**, when a provider and model are configured: title, Markdown notes, and speaker names offered as pending names to unresolved speakers (see [Speaker Names](#speaker-names)), kept on the transcript as an audit trail. Local Ollama runs inline; any other provider is handed to the IO lane (`generate_meeting_intelligence_task`). Without AI the recording still completes, and **Generate Notes** and **Retry Speaker Inference** work once AI is configured.
9. **Completion.** Auto-link to a calendar event, then queue the follow-ups in [backend/worker/tasks/followups.py](../backend/worker/tasks/followups.py): transcript indexing (IO), delivery (CPU), overlap (GPU) and, if the owner opted in, AI analysis (IO).

The playback proxy is built by `generate_proxy_task` on the CPU lane, queued alongside processing. `POST /recordings/{id}/reprocess` requeues the pipeline, optionally with a different engine and model (`engine_override`). A completed ordinary recording retains its previous publication until the replacement transcript and speakers commit; generated processing state, chat and transcript index rows are cleared at that boundary. The user's notes, documents and document index rows survive. Recordings with settled provenance retain their separate human-work reconciliation contract (see [Live Word Settling](#live-word-settling)).

Deferred notes, titles and speaker suggestions need no publication fence: reprocessing is refused while a recording is queued or processing or its notes are generating (409), and speaker inference holds it in processing for its whole run. In the recording view, retained transcript and speaker mutations stay disabled until the replacement snapshot has been accepted, including when completion metadata arrives before that snapshot or an active editor defers an old row.

A Meeting Edge call runs outside the transcript lock. Its result or error is stored only while the recording is still in the phase the run started in (capture, including a pause, or processing) and the same tab holds the capture; a run overtaken by Stop or a takeover only leaves its updating state, so the stored guidance stays. The recording view retains stored guidance regardless of the installation toggle, with focus and context controls read-only after capture ends; pending focus saves are cancelled at that transition. Run status and errors show only during capture. Error toasts apply only to active or paused capture and are deduplicated by recording ID and message.

### Final Speaker Pass

[final_diarization.py](../backend/processing/final_diarization.py) runs community-1, releases its model and CUDA cache, then runs offline Nemotron. This requires install-level `speaker_engine=auto`, CUDA, verified local assets and no recording speaker cap. Captures, imports and reprocessing share this path, independently of live labels. Offline inference processes the whole waveform with a CPU frontend and 340+40 settings (FIFO 40, cache update 300).

If Nemotron ever uses its eighth speaker channel, the pass returns community-1 unchanged. Otherwise [diarization_union.py](../backend/processing/diarization_union.py) keeps every native interval and adds community speech only outside native speech. Each community cluster takes the native identity with greatest total overlap, breaking ties by sorted label; clusters with no overlap get separate identities. Separate label namespaces prevent collisions, and merging same-label intervals prevents duplicate votes. Overlap and fragments under 0.1 seconds survive. The union cannot recover a second voice where native already hears another voice. Routing uses `float16(probability) > 0.5` on channel index 7; interval extraction uses float32 `> 0.5`. Exactly 0.5 is inactive in both.

CPU, `classic`, missing assets, a speaker cap or an absent/empty community result skip native loading. Catchable native failures keep community without retry or remote fallback; cancellation and time limits propagate. Native models are released in `finally` and by worker cache-clear hooks, before phantom filtering, VAD restoration, ASR, word alignment, consolidation, voiceprints and names. The [evaluation](evaluation/nemotron-710.md) separates live line accuracy from final diarisation error and reports ICSI's false-alarm rise and DER regression.

### ASR Engines

The engine and its model are install-wide settings.

- **Whisper** re-decodes a window by sampling when its greedy output fails a quality check. The sampling is seeded, so reprocessing on the same image gives the same transcript.
- **Parakeet and Canary** share `OnnxAsrEngine`. They transcribe in windows of 15 to 30 s that close at a pause (either may be shorter when less than 30.2 s is left), and skip a window with no signal (`_chunk_boundaries` in `onnx_asr_engine.py`).
- onnx-asr returns no token timings for **Canary**. The shared transcription dispatcher aligns each window against the exact audio it heard, using the pinned native Qwen3 forced aligner described below. Whisper and Parakeet keep their native timings.
- For **Parakeet** it returns each token's start only. `map_onnx_asr_recognition` ends each word at the earliest of the next word's start, the window's end, and its start plus `asr_word_length_cap_s` (default 0.4 s), never before the word starts. A word stretched across a pause could otherwise end inside the next speaker's turn and be given to them. The cap cannot exceed flip smoothing's default maximum word length (0.45 s), so a capped word stays short enough to smooth.
- **Parakeet** decodes once more any stretch of a decoded window (input of 30 s or less is one window) that holds 3 s or more of kept audio and no word, in calls of at most 20 s (`onnx_asr_backstop.py`). A stretch ends at the pause before the next word or 0.16 s before its stamp. It reads exact zeros as VAD silence, so it runs only when `VAD_MUTED_INPUT` says the audio the engine reads was muted: with VAD off, with `vad_mute_transcription` off, in the live lane and with Canary nothing changes.
- A stretch that retry leaves wordless is decoded a second time from the last subtoken of the word before it, keeping only the words that start inside the stretch. A stretch with no word before it in its window gets no second try.
- Invariant: a stretch is retried at most twice, and nothing is retried a third time. Stretches don't overlap, and neither do second tries, so the retries decode at most twice the window's own audio. One INFO line per recording counts both retries, what the second recovered or skipped, and what is still wordless.

#### Forced Word Alignment

Engines declare whether they supply native word timings. Only an engine without them requests the forced aligner; Canary is the current consumer, in both live and final transcription. Alignment runs before the common merge, live confidence payload builder and digital-silence word filter. Engine words use seconds relative to their input file; the alignment API maps observed boundaries to original character spans and absolute milliseconds, and the adapter converts them back to the engine clock. Live publication adds the recording offset once.

The aligner is `Qwen/Qwen3-ForcedAligner-0.6B` at revision `c7cbfc2048c462b0d63a45797104fc9db3ad62b7`, with a manifest of required file sizes and SHA-256 digests. Preparation writes a receipt; process-first loading independently verifies the bytes and rejects custom-code metadata. Alignment never downloads: without a verified receipt it fails fast and queues the `forced_aligner` preparation target through the same non-blocking, pending-marker request Nemotron uses, so the segment keeps its text without word timings. Engine preparation, including the API's startup preparation, makes the same request once the engine is ready rather than downloading the aligner on the GPU lane; every pinned preparation runs on the CPU queue. After a failed preparation, that request queues nothing for ten minutes (`FAILURE_BACKOFF`), so an offline worker does not queue one per live step; an explicit download from settings is not held off. Only native Transformers 5.20.2 classes and local safetensors load, with remote code disabled. Ordered load-time key mappings and an in-memory native configuration adapt the checkpoint without rewriting it. The checkpoint's Whisper feature-extractor configuration is promoted in memory to `Qwen3ASRFeatureExtractor`; upstream extraction pads the mel axis and mask to the native encoder's multiple of 100, including arbitrary window lengths. Every weight key and shape must match, loading diagnostics must be empty, and a source-owned alignment template supplies two timestamp markers per normalised token.

Alignment is **CPU only for now**, using one cached fp32 model with about **3.7 GB of RAM resident while loaded** for its weights, plus inference workspace. It never allocates GPU memory, so live ASR and Nemotron keep their GPU headroom even as their inference working sets grow. GPU placement may follow after hardware measurement of the maximum priority-model working sets. Forwards are serialised, batch one, in inference mode, with generation caching disabled. The single CPU profile is bounded to 60 seconds and 4,096 prepared tokens. Torch inherits the existing worker thread setting (`OMP_NUM_THREADS=2` in Compose); alignment does not change it.

An earlier offline CPU measurement on an Intel Core i7-13700K with two intra-op threads measured warm medians of **1.01 / 1.87 / 2.81 seconds for 10 / 20 / 30 seconds of audio**, respectively (one excluded warm-up and ten measured passes each; loading excluded). The 30-second window therefore adds about **5.6 minutes per hour of audio** at that measured cost. The reference text contains only eight words; this is a cost measurement, not a speech-dense throughput or target-host guarantee. That measurement used the previous whole-window rejection policy, which rejected zero-duration predictions in the 20- and 30-second samples.

Alignment preserves every original lexical span, including punctuation, and applies per-word retention. In text order, a span is timed only when its duration is positive, it lies inside the audio, and neither boundary precedes the corresponding boundary of the last retained word. Overlap is allowed. Other words retain their source spans with null start/end values; times are never snapped, interpolated or copied from neighbouring words. Missing lexical tokens, unsupported languages, model failures or a window with no retained timings keep the full original wordless window and an explicit `alignment_error`. A partially timed window is successful and has no `alignment_error`.

Timed words follow normal word-level speaker assignment. Untimed words stay in source order inside the preceding timed word's segment; a leading untimed run joins the following timed word. They never form separate envelope segments, and segment bounds come only from timed words. Splitting keeps each untimed run with its timed neighbour, preserving browser ordering without inventing word times. If silence filtering removes every timed word, final publication uses one wordless whole-window failure. Live context trimming retains unplaced words in a crossing window because their position is unknown, and repetition filtering leaves partial wording alone. The digital-silence word filter judges only observed word spans; unplaced words remain. Live and final canonical confidence evidence keeps all source words and null timings in the existing `asr_segments[].words[]` payload, with `asr_word_timestamps_available` true only when some word is timed. Whole-window failures replace previous alignment evidence and expose `alignment_error` through public utterance reads and browser state, retaining unrelated confidence and provenance fields. No separate untimed-word count field is added: the null entries are the evidence. Native Whisper/Parakeet behaviour is unchanged.

Each user's transcription language reaches live, final, import and reprocess ASR and is part of the ASR result hash. A recording can override it: `Recording.transcription_language` is `NULL` (the owner's setting, every existing row) or `auto` or a listed code, set at import, on reprocess (absent keeps it, `null` clears it, as with `max_speakers`) and by `PATCH /recordings/{id}`. It lives on the recording independently of each transcript publication. `apply_recording_language` lays it over the merged settings, so the language resolves recording, then owner, then `auto`, for final ASR and for every notes path (the pipeline's, the IO lane's, regenerate and AI analysis), which "Same as transcription" follows. The live lane uses the owner's setting. Whisper gets a language when one is selected, Canary gets its source-language parameter, and Parakeet always auto-detects. Canary can't detect a language, and onnx-asr prompts it with English when none is passed, so on automatic it resolves to `en` (`resolve_transcription_language_code`), and the result and hash say English.

- On automatic, Whisper would detect the language from the first 30 s of the file it reads: room noise in the unmuted file, mostly zeros in the muted one. So when VAD ran, the engine first detects on the first 30 s of speech in the VAD-muted file (`LANGUAGE_DETECTION_AUDIO`, each silence cut to 100 ms), whichever file it transcribes (the union file included, see [Muted Audio Per Stage](#muted-audio-per-stage)), and transcribes with that language (#671). Only the VAD stage sets the key. With VAD off, if that file holds no speech, or if the detection fails, Whisper detects on its own input as before.
- The same detection runs when a language is set, to check it: Whisper still transcribes in the set language, and the result carries `language_detection` (`detected`, `detected_label`, `probability`, and the Whisper `model`). Here detection is advisory: anything it raises is logged and the run goes on in the set language. The pipeline stores it on `Transcript.language_detection` with `used` (the result's language) and `engine`, or `NULL` when no detection ran, on every run. `RecordingPublicRead.language_notice` (`backend/utils/language_notice.py`) is computed on the detail read: a mismatch notice when the recording is `PROCESSED`, its `transcription_language` is `NULL`, and detection heard another language than `used` with probability at least `LANGUAGE_NOTICE_MIN_PROBABILITY` (0.5). Its `reprocess_language` is the detected code when listed, otherwise `auto`, and the reprocess keeps the notice's `model`. Both answers set `transcription_language`, so a notice cannot return after one. Parakeet and Canary installs have no Whisper weights, so they never detect.

### Words In Digital Silence

Whisper can emit a word or two, most often "Thank you.", in the silence the VAD stage muted to exact zeros. After transcription, `drop_unheard_words` ([backend/worker/tasks/final_segments.py](../backend/worker/tasks/final_segments.py)) reads the exact-zero runs of the audio the engine read and drops each word lying inside one run with `UNHEARD_WORD_GUARD_S` (0.5 s) of zeros to spare on each side ([backend/processing/unheard_words.py](../backend/processing/unheard_words.py)). A segment that loses every word goes too, a segment without word times is judged on its own span, and the result's text is rebuilt. A word that straddles the edge of kept audio, or sits nearer it than the guard, is kept, since word times stray a little from the sound they mark.

- It reads the zeros rather than the VAD's speech regions, so it only touches audio the engine heard as silence: the gaps between regions, the regions under the 250 ms minimum that the mute step zeroes, and the muted first and last second. On unmuted input, with VAD off or `vad_mute_transcription` off, the only runs are true digital silence, so a word outside the VAD's regions, often speech it missed, is kept.
- Every engine is treated alike. Successfully aligned Canary words use the same word-level filter; a window whose alignment failed is judged on its full segment span.
- It is best effort: audio that cannot be read keeps every word. The `final_asr_unheard_words` pipeline metric counts what went.
- The live lane does not run it. Finalise transcribes the recording again, so no live line reaches the final transcript.

### Muted Audio Per Stage

With `enable_vad` on, the VAD stage keeps two files: the normalised 16 kHz mono file, and a copy with every sample outside speech, and the first and last second, set to exact zero. Two per-user settings choose which one each stage reads (`muted_stages` in [backend/processing/vad_muting.py](../backend/processing/vad_muting.py), issue #486). `vad_mute_transcription` defaults to true, the muted file, and `vad_mute_diarization` to false, the unmuted one. The worker's merge applies no user defaults, so an unset, null or non-bool value takes the default in `VAD_MUTE_DEFAULTS`, which the user defaults in `config_manager` also read.

- `vad_mute_transcription` covers the engine and the zero-run drop above. `VAD_MUTED_INPUT` follows it, not `enable_vad`, so the Parakeet backstop runs only on muted input.
- Muted transcription mutes only where neither VAD nor diarisation heard speech (issue #670). When diarisation heard the unmuted file and returns turns, `transcription_audio_after_diarization` ([backend/worker/tasks/vad_stage.py](../backend/worker/tasks/vad_stage.py)) writes a third file, `*_vad_union.wav` (`write_union_muted_audio` in `vad_muting.py`): the muted file, with the unmuted samples put back inside every turn after the phantom filter, except the turns of a cluster it confirmed as non-speech (issue #678). Those stay in the diarisation, relabelled to the nearest speaker so their words keep one, but open nothing: only VAD's own speech in them is heard, unless another speaker's turn covers the same stretch. `run_phantom_filter` keeps their `(segment, track)` keys on the run's context for the union. The first and last second stay muted. The engine, the backstop and the zero-run drop read it, with `VAD_MUTED_INPUT` set. Silero trims the edges of words and drops short replies that pyannote still hears: on four AMI meetings, 10 to 12 % of diarised speech time was VAD-muted, in stretches with a median of 0.18 s. With diarisation off, failed or empty, with `vad_mute_diarization` on, or if the file cannot be written, transcription reads the VAD-muted file. The log's one `Transcribing` line, written once diarisation has run, names the file.
- `vad_mute_diarization` covers diarisation, the phantom filter and final-pass voiceprint extraction, which score the clusters diarisation found. Voiceprint rebuilds always read the source recording.
- Invariant: muting zeroes samples and never cuts them, so every file has the same rate, length and time base. Word times and turn times need no offset whichever file each stage read.
- Invariant: inside a turn other than a confirmed non-speech one, outside the first and last second, the union file is the unmuted file; everywhere else it is the muted file. So it never mutes a sample the muted file kept.
- VAD runs whenever `enable_vad` is on, so the no-speech short-circuit holds with both switches off. With `enable_vad` off, both stages read the unmuted file, whatever the switches hold.
- A word that unmuted transcription places more than `GAP_WORD_TURN_TOLERANCE_S` from any turn of a muted diarisation stays `UNKNOWN`: hidden in the transcript view, left out of Meeting Chat's transcript and counted as unattributed, but kept in exports, meeting notes and `transcript.text`.

### Word Timestamps In The Merge

`combine_transcription_diarization` in [backend/utils/transcript_utils.py](../backend/utils/transcript_utils.py) treats each run of consecutive segments by what it has. A run with word timings is aligned word by word; a run without (Canary, or a Whisper segment with an empty `words` list) gets each segment's dominant speaker. Every segment's text reaches the output. A word no longer than pyannote's segment precision takes the speaker whose turn contains its instant (`[start, end)`; a turn's end counts when no turn starts there). A word that overlaps no turn takes the speaker of the nearest turn within `GAP_WORD_TURN_TOLERANCE_S` (0.5 s), the earlier turn on a tie, unless the attributed words either side share a speaker with a turn that near, whose speaker it takes. Neighbours are read as diarised, before any gap word is given a speaker. A word further than that from every turn stays `UNKNOWN`. Single-word flip smoothing then gives a word of at most `word_flip_max_duration_s`, within `word_flip_max_gap_s` of neighbours that share a speaker, to that speaker.

Consolidation never drops text. A segment under 0.1 s folds into a neighbour at most 1.0 s away if the result stays within 30 s, preferring the same speaker and then the nearer one; the receiver keeps its speakers. A fragment with no qualifying neighbour stays as a short segment, and only a fragment without text is dropped. Neighbours whose fragments all folded away merge only if the original pieces tiled (gaps under 0.01 s) with the same speakers, within 30 s. Overlapping turns with different credited speakers keep separate lines. Word grouping still breaks on speaker changes and gaps greater than 1 s. A segment over 30 s prefers the sentence end nearest 30 s in the 24–36 s window, otherwise the nearest word boundary in that window; with sparse timings it uses the last boundary at or below the target, allowing one indivisible word to exceed it. The existing soft window scales with an explicit custom cap. Without timings, proportional text splitting near a space retains the full wording. Final consolidation and both live lanes share `DEFAULT_MAX_SEGMENT_S` from `backend/processing/live_limits.py`; the legacy `live_max_segment_s` setting can override live limits. No migration rewrites stored transcript lines.

Invariant: float rounding decides no threshold on a word time, or on a gap or duration built from word times. Parakeet times sit on onnx-asr's 80 ms grid (or the cap past it) and Whisper's on hundredths of a second, so a gap can equal a threshold exactly. Every such comparison, in the mapper, the merge, flip smoothing, consolidation, the fold and the live lane's context trim, goes through [backend/utils/word_times.py](../backend/utils/word_times.py), which treats a value within 1 µs of its threshold as equal to it. Speaker-overlap ratios are not word-time thresholds and compare as they are.

### Processing Tuning

Eight values in these stages can be overridden. Keys, defaults and bounds live in [backend/processing/processing_tuning.py](../backend/processing/processing_tuning.py), which imports nothing heavy so the API validates against the same table, and the processing modules take their defaults from it. [frontend/src/lib/processingTuning.json](../frontend/src/lib/processingTuning.json) mirrors it.

| Key | Stage |
| --- | --- |
| `vad_threshold` | VAD, final and live |
| `asr_word_length_cap_s` | Parakeet word ends, final and live |
| `phantom_max_duration_s`, `phantom_max_segments`, `phantom_embedding_floor`, `phantom_merge_threshold` | Phantom filter |
| `word_flip_max_duration_s`, `word_flip_max_gap_s` | Flip smoothing |

Defaults and ranges are in [DEPLOYMENT.md](DEPLOYMENT.md#processing-tuning-defaults).

Either phantom ceiling at 0 turns the phantom filter off, and a `word_flip_max_duration_s` of 0 turns smoothing off.

Each value is a per-user setting. A stage resolves it as an explicit argument, else the recording owner's merged settings (their value over the install's flat `config.json` key), else for VAD the install's `vad_parameters.threshold`, else the shipped default. User defaults stay `None` (inherit), because the settings page autosaves the whole object and a concrete default would be written onto every row.

A tuning value never fails a recording. The API rejects out-of-range values, but a stored value can still be unusable (hand-edited, restored from a backup, or saved before a bound tightened), so the worker logs it and uses the shipped default (for VAD, `vad_parameters.threshold`). The phantom floor must be below the merge threshold: the API checks the pair the worker will read, and the worker treats a conflicting pair as both defaults. GET returns the install's flat values as a read-only `processing_tuning_install` map so the settings page can run that check. New code must read these values through `resolve_tuning`, or `get_vad_config_from_settings` for VAD.

### Transcription Failure Versus Silence

Invariant: an empty `completed` transcript means the meeting was silent, never that ASR failed.

An engine's `transcribe()` returns the canonical result or raises `TranscriptionError` ([backend/processing/engines/errors.py](../backend/processing/engines/errors.py)), never `None`; empty text with no segments is a success. The dispatcher `transcribe_audio` wraps anything else an engine raises, so `TranscriptionError` is the one exception callers treat as a lost transcription, and code that calls an engine must not turn it into an empty result. The message is written for the UI. `gpu_out_of_memory` marks a GPU out-of-memory failure, which counts only when the model ran on CUDA (an onnx-asr model on CPU reports the server out of memory). After an out-of-memory error the engines drop every reference to the model, including those held by the traceback's frames, so the memory is freed. Celery time limits and termination are re-raised unchanged.

Final processing retries a GPU out-of-memory failure once, after releasing every cached model and the CUDA cache. A failure that remains sets `transcript_status` to `error` with the message in `error_message`, marks the recording `ERROR`, and stops before the merge and everything after it. Diarisation has already run, and its result is discarded. Provisional live text is kept. Only reprocessing repairs it; **Retry Speaker Inference** refuses it, and a run that finds the transcription failed returns the recording to `ERROR`.

`error_message` is shared with notes failures, and `transcript_status` decides whose it is. Only the `Transcript` methods `fail_transcription`, `complete_transcription` and `set_notes_error_message` write it, which keeps a notes run from clearing a transcription failure; a backup restore that settles an interrupted recording uses the same path. Notes cannot be generated for a failed transcription: the API answers 409 and a notes task already queued does nothing. A later run that completes clears the failure, and if it finds no speech it leaves `notes_status` alone.

### Speakers And Voiceprints

`Recording.max_speakers` is an optional upper bound, settable at import, on reprocess and during a live capture. `NULL` (the default) passes no speaker keyword to pyannote. A value is passed as `max_speakers`, never `num_speakers`, because an exact count forces a split whenever the user overcounts.

A person (`global_speakers`) belongs to one user (`user_id`). Identification, the voiceprint dialog, renames and every other lookup read only the people of the recording's owner, so a recording speaker links only to a person in its owner's library.

Voiceprints are comparable only within one extraction procedure. `EMBEDDING_METHOD_VERSION` in [backend/processing/embedding_version.py](../backend/processing/embedding_version.py), which imports no torch, is stored on `global_speakers.embedding_version` and `recording_speakers.embedding_version`. Identification and the duplicate-merge pass refuse to score across versions. Any change to how embeddings are produced must bump the version, and any new comparison must check `embeddings_are_comparable`. Thresholds are in [backend/processing/embedding.py](../backend/processing/embedding.py).

Every write must keep a stored voiceprint's version true:

- A freshly extracted vector is stamped `EMBEDDING_METHOD_VERSION`.
- A copied voiceprint (restoring a backup) keeps its own version.
- A blend goes through `blend_voiceprint`, which never mixes versions. A current voiceprint replaces a stale one without the drift guard, since a cosine across versions says nothing; a stale one leaves a current row unchanged; an empty row takes the incoming vector and its version.

The duplicate-merge pass (`backend/processing/speaker_merge.py`) joins clusters the diariser split from one voice:

- The threshold is `DUPLICATE_SPEAKER_MERGE_THRESHOLD` (0.70). Lowering it causes wrong merges, which are harder to undo than wrong splits.
- Linkage is complete: two groups join only when every pair across them clears the threshold, so no third cluster can bridge two people.
- A group carrying a person's identity is held to that person's library voiceprint. If any cluster in the proposed union, other than those already identified as that person, scores below `IDENTIFIED_MERGE_VOICEPRINT_FLOOR` (0.60, deliberately not tied to `DRIFT_GUARD_THRESHOLD`), the union is refused and that cluster keeps its `Speaker N` name. A library voiceprint from another extraction version is not consulted.
- Each finalised utterance keeps its diariser cluster in `transcript_utterances.diarization_label`, so `unmerge_recording_speaker` can restore a merged cluster as an unnamed speaker with all its lines except those a person assigned by hand, recording an `unmerge_speakers` correction event. Lines written before that column existed carry no label; undoing those merges needs a reprocess.
- Overlap labels are left as diarised in the `Transcript.segments` projection, and `serialize_canonical_utterances` resolves them on read: a merged speaker's label reads as the speaker it was merged into, and a label that resolves to the line's own speaker is dropped. A merge made in the speaker panel therefore leaves no raw label in an overlap lane, and an unmerge brings the label back. Processing's own merges rewrite overlap labels before finalise, so undoing one of those leaves them on the survivor.

Every link of a recording speaker to a person offers its voiceprint through `update_library_voiceprint` in [backend/processing/embedding.py](../backend/processing/embedding.py):

- **Speech floor.** Only a recording voiceprint with at least `LIBRARY_VOICEPRINT_MIN_SPEECH_S` (20 s) of speech founds a library voiceprint; a shorter one links without it. Every extraction records the figure on `recording_speakers.embedding_speech_seconds`. An unmeasured voiceprint founds as before, and nothing re-extracts just to measure. `RecordingVoiceprint.from_task_result` refuses an extraction result with no figure, so a result from an older worker is never grandfathered as unmeasured.
- **Figures follow extractions.** Speech is never pooled across recordings. A merge within one recording adds the figures when its fold passes the guard, and an unmerge takes them out.
- **Drift guard.** A fold is refused when `cosine(current, incoming) < DRIFT_GUARD_THRESHOLD` (0.70).
- **Refusals stay on the link.** A link keeps every person the guard refused it for, one row each in `recording_speaker_drift_refusals`, keyed by the link and the person. A `skipped_drift` link gains a row for that person, and a later save or fold of the link into them deletes only their row (`record_drift_verdict`). A link a lock keeps out (`skipped_locked`) is judged against the locked voiceprint instead (`judge_drift`); any other outcome is no verdict. While the speaker is linked to a person it has a row for (`is_drift_refused`), every rebuild or pooling of that person's voiceprint from links leaves it out. A save, fold or refusal for someone else leaves the row alone, so a link that returns to that person without a new verdict is still left out.
- **A new voiceprint is judged.** A segment moved onto the link, a speaker merged into it, the voiceprint dialog's extract and the extract-all endpoint, and a processing run that finds the speaker already there (named during capture, or a run requeued after an interrupted one) each give the link a voiceprint offered to no one. The guard compares it with the voiceprint of the link's person, which stays as it is (`judge_drift`): a refusal adds or keeps that person's row, a pass deletes it, and rows for anyone else stay. With no person, or no voiceprint of the same version, nothing changes.
- **Other changes.** A split's remainder deletes all of the link's rows (`forget_drift_verdict`), since the split decides whether it joins the original person. Re-extracting the same speech after a method change keeps them. Reprocessing deletes the recording's speakers, and their rows with them. Merging two people moves the source's rows to the target, keeping one where a link was refused for both. Deleting the link or the person deletes its rows (`ON DELETE CASCADE`).
- **Locks.** `is_voiceprint_locked` blocks the pipeline's fold, auto-applied name suggestions and segment learning. Every user action that would change a person's voiceprint shares one rule (`lock_blocks_user_link`): a rename on either write path, **Add to People** into an existing person, the voiceprint dialog's link, and merging another person into them. The lock blocks any change to an existing voiceprint, a stale one included (`skipped_locked`), but a locked person with none still gets one. The user's explicit overrides are the dialog's force link (`force_link`), which folds through the guard and leaves the lock set; recalibrating and a split, which set it; and deleting the voiceprint, which clears it. The person update (`is_voiceprint_locked`) sets or clears it alone, leaving the voiceprint as it is. A lock never stops identification.
- **Confirmed names teach.** With the owner's `voiceprint_learning` at `confirmed` (the default), a person's library voiceprint learns only from links the user made or confirmed, or from before sources were recorded (`link_teaches_library` in [backend/utils/speaker_names/sources.py](../backend/utils/speaker_names/sources.py): locked, as every rename, link and Confirm leaves a speaker, or `name_source` NULL). A confident voiceprint match at the final pass folds nothing (`_learn_from_confident_match` is skipped), a name taken as given by `confirm_suggested_names` links without offering the voiceprint, a segment moved onto an unconfirmed link doesn't reach the person, and the rebuild task and a split's fallback to other recordings leave unconfirmed links out. Confirm is a rename, so it offers the voiceprint as a rename does. `automatic` restores learning from every link. User acts, locks, the drift guard and the thresholds are unchanged.
- **Versions.** A current voiceprint replacing a stale one is a founding and needs the floor.
- **Pooling.** Recalibration and a person split extract one voiceprint per selected recording (`pool_recording_voiceprints`) and average only those that meet the floor. Recalibration alone overrides the guard: in each recording it uses, it lifts the refusal of the person's links with a line its samples cover more than half of.
- **Splits.** The original person is rebuilt from their remaining clips, else from their unrefused links in other recordings (`saved_from_other_recordings`), and cleared only if neither qualifies, since the old voiceprint holds the moved clips. A cleared row keeps the current `embedding_version`; a NULL one reads as legacy and the rebuild task would found it again. An original with one speaker in a split recording gives that speaker the remainder's voiceprint, so a rebuild can't average the moved clips back in. The receiving person is locked when the split saves or folds their voiceprint; the original keeps their lock unless their voiceprint is cleared.

`rebuild_voiceprints_task` repairs stale voiceprints from Celery Beat every six hours, at most 25 recordings a tick (`AUTOMATIC_VOICEPRINT_REBUILD_LIMIT`). A stale voiceprint that cannot be re-extracted (its audio is gone, or its speaker has no transcript segment) is cleared; a transient failure leaves it for the next run. It averages only unrefused links that meet the floor, without re-running the guard, since a cosine against an old-version voiceprint means nothing, and skips a person with a locked current-version voiceprint. A stale person with no qualifying current-version speaker keeps the stale voiceprint, which matches nothing; only one with no current-version speaker at all is cleared.

A speaker correction (a rename across the recording or from an utterance forward, a merge, a library link or promotion) changes only the utterances its scope selects, or the speaker's identity. It never re-derives other utterances from `diarization_window_results` or `diarization_window_turns`, which hold data only for live captures finalised by v1.0.0 to v1.2.0.

The following `pipeline_metric` stages make diarisation and naming quality readable from the logs:

- `final_diarization_invocation`: `speaker_pass` is attached before processing and records the route (`union`, `community_channel_7`, `ineligible`, `failed` or `interrupted`) and its reason. Native work is marked as running before it begins; interruptions propagate with their exception class and a nonempty metric error.
- `final_diarization_speaker_stats`: per-cluster speech duration, segment count and share, overlapped speech, and whether the cap bound.
- `speaker_identification`: each cluster's three closest people with cosine scores, and which matched.
- `speaker_merge_pass`, emitted on every run, including runs that merge or score nothing (with a reason): pair scores, why a pair over the threshold was refused, each merged group with its survivor and scores, and each absorbed cluster's score against the person's library voiceprint.
- `speaker_name_resolution`, one per standing name event: the speaker holding its span, the share held, whether it was applied, offered as pending (`unplaced` for a user's name that landed on nobody) or left unresolved, and the floor score of a linked person.
- `speaker_name_reviewed`, one per Confirm or Not {name}: the speaker's label, the answer and the source of the name it answered.

#### Speaker Names

Every naming act on a recording's speakers is a row in `speaker_name_events` ([backend/models/speaker_name_event.py](../backend/models/speaker_name_event.py)), owned by the recording and only ever added to. A row holds the name, the person if any, the source, its authority and the span of the meeting the name was given for (`anchor_start_ms`, `anchor_end_ms`). Sources rank a self-introduction (`heuristic`, 10) below the LLM (20), a voiceprint match (30), a name confirmed by the confirm-at-end setting (`auto`, 35) and the user (40). A later act on the same speaker supersedes the earlier row (`supersedes_event_id`), so the table is the audit trail of how each speaker got its name. `recording_speakers.name_source` records which source gave the name a speaker shows; NULL is a name from before sources were recorded, or "Speaker N".

- **User acts.** A rename, a link to a person and **Add to People**, on the web app or through MCP, write a `user` row anchored on the speaker's longest turn so far: consecutive lines with one speaker, gaps under 1.5 s ([backend/utils/speaker_names/anchors.py](../backend/utils/speaker_names/anchors.py)). So do the voiceprint dialog's link and a line moved to a person that adopts the speaker of that name (`record_user_link`). Each leaves the speaker locked with `name_source` `user`, on either write path. A speaker with no lines gets no row. Each also keeps writing its `speaker_correction_events` row. Merging two people moves each link to the target and confirms only the speakers that were confirmed, whose new row names the target: an unconfirmed match stays unconfirmed, with its source, and no row is written for it. A People scan for matches links as a voiceprint match (`link_voice_match`), unconfirmed, with its cosine as `identity_confidence`. It skips a speaker the user named or confirmed, one that keeps any other name of its own (a pending self-introduction or AI name gives way), and one the user dismissed that person for.
- **At the final pass**, before identification, the machine rows of any earlier run are dropped (this run derives its own) and every standing row goes to the final speaker holding at least 60% of the attributed speech in its span (`resolve_names` in [backend/utils/speaker_names/resolve.py](../backend/utils/speaker_names/resolve.py), pure). A live row's span is every live line of its `anchor_label`, superseded ones included, rather than its anchor turn (`live_label_spans`), since the final transcript need not cover that turn. A span with under 1 s of attributed speech names nobody, unless the row is the user's: a user's name is never dropped silently, and is offered as pending on the speaker holding the most of what speech there is, else on the speaker nearest in time. Each speaker takes the highest-authority name among the rows it holds; within that authority, a name needs 60% of the summed overlap.
- **Stop rule and floor.** A held user name stops identification for its speaker, which is locked as a rename leaves it. A user name for a person applies only if the cluster scores at least `IDENTIFIED_MERGE_VOICEPRINT_FLOOR` (0.60) against that person's library voiceprint; when either side has no voiceprint of the same version, the user's word stands. The carry-over teaches no library voiceprint: the act that wrote the row already offered the voiceprint when it was made.
- **Pending.** A span no speaker clearly holds, a user's span that landed on nobody, two names too close to call, and a person the floor refused are offered as pending names, applied after the merge pass to the surviving speaker of the label they landed on, and only to a speaker still unnamed and unlinked, so they never block a merge, trigger merge-by-name or override a voiceprint match.
- **Inferred names are pending.** A self-introduction or the LLM's name ([backend/worker/tasks/speaker_name_apply.py](../backend/worker/tasks/speaker_name_apply.py)) becomes the speaker's local name with its source and no lock, and writes a row: a self-introduction on its own line, the LLM's name on the speaker's turn nearest its evidence, else the longest turn. It links nobody in People and offers no voiceprint. A voiceprint match keeps its provisional link and writes a `voiceprint` row on the cluster's first turn, with its raw cosine as `identity_confidence`. A name is pending (`name_is_pending`, serialised as `name_pending`) while it has a machine or carried source and no lock; NULL and `auto` names never are. A `voiceprint` name at or above `PLAIN_NAME_MATCH_SCORE` (0.85) also shows plain, without becoming locked or teaching the library under confirmed-only learning. A pending heuristic or LLM name on a speaker linked to nobody may be replaced by the next inference, and an earlier run's pending name does not count as the user's.
- **Confirm and dismiss.** `POST /speakers/recordings/{id}/speakers/{label}/suggestions/accept` is the rename to the name shown, so it links People by exact name, locks, offers the voiceprint and writes a `user` row; `.../suggestions/reject` writes a `dismiss` row, clears the name and any link, and puts back the speaker's own `Speaker N` (from its label, unless another speaker shows that number). Confirm answers 409 for a speaker with no pending name; Dismiss also accepts an unlocked `voiceprint` name, including a strong match shown plain. Both close the suggestion's `speaker_name_suggestions` entry as `accepted` or `rejected`. A dismissed name is never applied to that speaker again. The `speaker_name_reviewed` metric records each answer and the source it answered.
- **Confirm at the end.** With the owner's `confirm_suggested_names` setting on (off by default), names are taken as given, as before this change: `name_source` is `auto`, and an exact People name links that person. The voiceprint is offered only under `voiceprint_learning: automatic` (see [Speakers And Voiceprints](#speakers-and-voiceprints)).
- **Live names.** `PUT /speakers/recordings/{id}/live/{label}` ([routes_live_names.py](../backend/api/v1/endpoints/speakers/routes_live_names.py)) names a live label (`LIVE_PROVISIONAL_<n>`) while the recording is `UPLOADING` or `PAUSED`, checked with the recording row held `FOR NO KEY UPDATE` until the row commits: a stop's status change waits for a name in flight, and a name sent while a stop is committing waits for it and is refused (409), never written after the final pass has read the rows. It writes a `user` row with surface `live`, `anchor_label` the live label and no recording speaker, anchored on the label's longest locked turn, or its longest turn when none is locked or the locked one is under the final pass's 1 s floor; an unlabelled line ends a turn ([backend/utils/speaker_names/live.py](../backend/utils/speaker_names/live.py)). It supersedes the label's previous live row, so one name per label stands. An exact People name links that person; nothing creates one, and nothing is learned. A placeholder name (`Speaker <n>`, `SPEAKER_<n>`, `Unknown`) is refused (422), since the final pass merges speakers that share a name. The live read (`GET /transcripts/{id}/utterances`) returns `live_speaker_names` (label to name) whole on every read, delta or not, for the labels a current line still carries, so it is empty once the final pass has replaced the live lines; every reader that shows a live label as "Speaker <n>" shows the name instead. The final pass carries the row like any user row above, placed on all of the label's live lines, so the floor checks a person link and nothing teaches a library voiceprint before the speaker is locked.
- **Live speakers as line targets.** While the recording is `UPLOADING` or `PAUSED`, **Change speaker** on a line can pick a live label: the line keeps the raw label with its manual lock and no `RecordingSpeaker`. The speaker-change route checks this as live names are checked (`publication_is_current` under the Transcript fence, else 409), and takes a live label for that one line only (`utterance_only`, else 409), since a whole live speaker joins another by a merge (below); the MCP correction tool calls the same route. The picker lists live labels only in the live view, once each, by their current name; a name is display text, never an identity key. The final pass sends each such line where the label's name goes, in `carry_names_to_final_speakers`: a named label reuses its name's placement, an unnamed one is placed the same way on the same speech, which is the label's live lines less those moved by hand. That is the holder, the top holder when no speaker holds 60%, or for under 1 s of attributed speech the speaker holding most of it, else the nearest. An unnamed label with no speech of its own left, every line of it moved by hand, gives each line to the final speaker of its own span; a named one still sends them where its name goes. The lines move after the merge passes, to the surviving speaker, as pending names do, under the Transcript lock and then the lines' own, before canonical finalisation inherits them. No processed line keeps a live label.
- **Live merges.** `POST /speakers/recordings/{id}/live/{label}/merge` (`into_label`) merges one live label into another under the same check and lock as live names, refusing a merge within one group (422). It writes a `user` row of kind `merge` with surface `live`, `anchor_label` the merged label (after earlier merges, its group's) and `evidence.into_label` the label it joined, superseding the merged label's own live row, so its name stops standing; a merged label's target survives in `settling_state.name_anchors` with the row ([backend/utils/speaker_names/live.py](../backend/utils/speaker_names/live.py)). Merges chain (`live_groups`: merging a label moves its whole group), naming a merged label names its group, and no line is rewritten: the live read returns `live_speaker_merges` (label to the label it joined) whole on every read, `live_speaker_names` gives a merged label its group's name or "Speaker <n>", the live feed shows a merged label's lines under the label it joined, and live analytics counts them there. At the final pass, in `carry_names_to_final_speakers`, a group is one live speaker: its name and the lines moved to it are placed on all of its labels' own speech. Each member label's own final speaker is folded into the group's ([backend/utils/speaker_names/live_carry.py](../backend/utils/speaker_names/live_carry.py), merged as a merge-by-name is, so **Undo merge** lists it) only when the group is held at 60%, that speaker holds 60% of the member's own speech, no other live speaker is placed on it, and 60% of the live-labelled speech it holds is the group's. Otherwise the member's own live lines go to the group's final speaker as lines moved by hand do, with the user's manual speaker, so no final speaker the user did not merge is merged. The `live_speaker_merges_carried` metric records each fold and line-by-line move.
- With no naming rows and no line moved to a live speaker, speaker assignment is as before.

A final pass meets user rows on a run that does not reset the recording, such as one requeued after an interrupted worker, and on a settled recording's reprocess, which keeps the user's rows (and their copy in `settling_state.name_anchors`) and replaces only the machine rows. Reprocessing an ordinary recording deletes every row, as it deletes correction events.

### AI Calls

- **Language.** The notes language is separate from the transcription language. Notes, meeting intelligence, title generation and secondary fallback all get the same output-language instruction. Prompt control text and JSON keys stay fixed, and the automatic intelligence contract accepts any non-empty top-level Markdown heading.
- **User notes** are anchored on the audio timeline and reach every notes, Meeting Edge, chat and speaker prompt; see [Timeline Notes](#timeline-notes).
- **Transcript reads.** Notes, Meeting Edge and Meeting Chat read segments through `build_transcript_segments_for_read` (the canonical utterances, else the `Transcript.segments` projection) and name speakers with `build_recording_speaker_map`. The canonical read runs in a savepoint, so a failure leaves the caller's transaction usable. Chat renders through `render_transcript_for_llm` (`backend/utils/llm_transcript.py`) as `[MM:SS]` lines, without the `UNKNOWN` lines the transcript view hides, with the user's notes inline; notes generation still sends them. The pipeline's first-pass intelligence and the MCP `get_transcript` tool format their own lines.
- **Meeting Chat** sends the notes and full transcript every turn, plus excerpts from the search index (`_chat_retrieval_filters` in `routes_chat.py`): documents attached to this meeting or to meetings its tags bring in, and transcript excerpts from those other meetings only. The index is rebuilt only after processing, so its excerpts can predate an edit. Chat also accepts in-flight recordings, using the shared canonical/projection renderer with current live names and timeline notes. Its prompt and interface identify the transcript so far and warn that wording and speakers may still change. The CLI path uses the same provisional context. Polling does not regenerate prior answers. The prompt also says what chat can do (`build_chat_context` in `backend/utils/chat_prompt.py`): answer from what it was sent, and nothing after the reply. Only a request that sends the `update_meeting_notes` tool (the streamed Anthropic, OpenAI and Gemini chats on a finished transcript) says it can change the notes; Ollama and subscription chats, and every chat on an in-flight recording, whose notes the running pass writes when it finishes, say they cannot.
- **Prompt caching.** Chat sends the notes and transcript as the system prompt (Anthropic marks it with `cache_control`; OpenAI-compatible providers reuse it through prefix caching), leaving history and the question in the messages. Meeting Edge and AI analysis split their prompts into a stable instruction prefix, which Anthropic marks, and the per-call context.

Prompt speaker labels resolve an unassigned `UNKNOWN` label to **Unidentified speaker**, so Meeting Edge, Meeting Chat (live or finished), other AI features and the MCP `get_transcript` tool do not treat the storage sentinel as a participant's name. Analytics, live and final, lists unassigned speech as **Unattributed**, as it already did for lines with no label. This rendering does not change stored labels or transcript and export display names.

#### Ollama Context Window

Left at its defaults, Ollama cuts an oversized prompt from the front (current releases keep about half the window) and shifts the context when the answer fills it, both ending in an ordinary stop. Hosted providers reject an oversized request. `OllamaLLMBackend._post_chat` therefore makes Ollama refuse instead:

1. `num_ctx` is `ollama_context_window` (the operator's VRAM budget, default 32768), lowered to the model's trained context from `/api/show` when that is smaller and never raised. `/api/show` is cached for five minutes per server and model.
2. Every `/api/chat` request carries `truncate: false`, which makes Ollama answer an oversized prompt with HTTP 400 before generating (0.34 and later include the token count), and `shift: false`, which ends an answer that fills the window with `done_reason: length`. No `num_predict` is sent, leaving a Modelfile's own limit in place. The 400 becomes a context-window error and a length stop an incomplete-answer error; neither answer is used.
3. Meeting chat drops the oldest turns itself, estimating 2.6 UTF-8 bytes per token and leaving a quarter of the window (at most 2,048 tokens) for the answer. The last message, which carries the meeting context and the question, is never cut. If Ollama still refuses, chat retries once with fewer turns, then reports the refusal.
4. Servers before 0.12.6 ignore both flags, so their token counts are checked after the call, and a prompt plus answer past `num_ctx` is refused as truncated.

A refusal raises `ContextWindowExceededError` (`backend/utils/context_window.py`), which the Ollama backend re-raises unwrapped. A secondary provider takes over as for any primary failure, including a streamed chat, since the refusal arrives before the first token. A length stop at the end of a streamed answer, or a truncation found after the call on an old server, withdraws the answer with no fallback. Speaker suggestions and document pages report the refusal as their error. Notes and chat continue as below.

#### Meetings Longer Than The Context Window

For long meetings, use a hosted provider, or Ollama with a hosted secondary that receives the whole meeting after Ollama refuses it. Only when there is no secondary, or it also fails, does Ollama write the notes in parts. `SecondaryLLMBackend` re-raises the primary's refusal, so the worker sees the same `ContextWindowExceededError` either way and calls `generate_meeting_notes_in_parts` (Regenerate Notes) or `generate_meeting_intelligence_in_parts` (the automatic pipeline), which the wrapper sends to the primary. The steps are in `backend/utils/long_meeting_notes.py`, with the splitter in `backend/utils/transcript_parts.py`:

1. **Budget.** Ollama 0.34 and later report the refused prompt's token count, which gives this meeting's tokens per byte, plus a tenth for parts denser than the whole. Without a count, parts are priced at 2.2 bytes per token.
2. **Split.** The transcript is split between lines (utterances and anchored notes, a note kept with its line where it fits) into the fewest roughly equal parts that fit, never fewer than two. An utterance longer than a part is cut between sentences, each piece keeping its timestamp and speaker. A part's room is the window less a quarter for the answer (at most 8,192 tokens) and less the rest of the prompt. If that leaves under a quarter of the window, the run is refused with a message naming the attached documents, the part of the prompt that grows without limit.
3. **Draft.** Each part is drafted with the same prompt prefix (instructions, speaker labels, metadata, glossary, user notes, calendar context, attached documents and the notes structure), followed by the part's number, times and transcript, so a server that keeps its prompt cache reads the prefix once. A draft Ollama refuses, or whose answer runs out of window, is halved and both halves drafted.
4. **Combine.** Combining calls keep a third of the window (at most 16,384 tokens) for the answer, leave out the attached documents, and are priced as prose at 2.5 bytes per token. Word targets let about three drafts share a call, and drafts too many for one call are combined in groups, then the groups. A refused combining call is halved, and two drafts Ollama will not combine end the run with an error. Each call is retried once after an Ollama server error.
5. **Speakers and title** (automatic pipeline). Calls in parts answer in Markdown with tagged lines, because a small model held to `format: json` over dozens of calls often loops or abandons JSON. Each draft lists the unresolved speakers its part gives evidence for in a `<speaker_names>` block. A speaker who introduced themselves is named by `detect_rule_based_speaker_suggestions`, as in a run without AI. A name every part agreed on is kept. For a label the parts disagree on, the final call picks one of their suggestions or none, and only an exact match counts, since names are applied without review. The final call also writes a `<title>` line, and names go into the notes afterwards with `apply_speaker_mapping_to_notes`.

A meeting that fits keeps the single call and a byte-identical prompt.

When every provider has refused the whole transcript before any text streamed, Meeting Chat asks once more with excerpts. `_transcript_excerpts` in `routes_chat.py` finds this meeting's most relevant transcript chunks by the question's embedding, and `render_transcript_excerpts_for_llm` reads the lines at those times from the canonical transcript, which picks up edits made since indexing. Lines are taken most relevant first up to the room left and shown in time order with `[...]` at each gap. On Ollama that room is the window less the answer room, the notes, the question, and up to an eighth of the window for recent turns. The prompt says the excerpts are partial. With no query embedding or no index for the meeting, chat answers from the notes alone and says so.

In-flight Chat, while the recording is in flight and its transcript is not yet completed, keeps the existing chat path and does not retrieve recent passages from an index. Regenerating notes or speakers on a completed transcript answers as a finished meeting. If the model refuses the transcript so far as too long for its context (`ContextWindowExceededError`), Chat retries with the most recent half of it, then a quarter and so on, keeping the notes legend, and says so in the prompt. A brief footer saved with each successful live answer says it used the provisional transcript and whether it was trimmed, so the notice survives a history reload. Finished meetings retain the indexed-excerpt fallback described above; document and related-meeting retrieval keep their ownership filters in both states.

#### Timeline Notes

The user's notes are `timeline_notes` rows (`backend/models/timeline_note.py`) at `/transcripts/{recording_id}/timeline-notes`, for the recording's owner only (anyone else gets 404).

- **Owned by the recording**, not the transcript, so a reprocess keeps them. Notes and tombstones go with the recording (`ON DELETE CASCADE`).
- **Kinds.** `point` (`anchor_ms`), `selection` (`quoted_text` over `start_ms`..`end_ms`), and untimed `head` and `tail`, each shape fixed by a check constraint and the API schemas. MCP `append_meeting_notes` adds a tail note, or a point note with `at_seconds`.
- **Times** are milliseconds of audio without paused time, the clock both transcripts share. During capture the detail endpoint reports `live_audio_ms` (`backend/utils/live_audio_clock.py`): the end of the last segment, run on from its arrival or from the last resume, whichever is later. The page runs it on between polls only while capture advances (`frontend/src/lib/notes/audioClock.ts`), so every device anchors alike. While capture advances the page's clock never runs backwards; a pause sets it to the paused figure, which is exact.
- **Reading them.** The detail read carries `timeline_notes_list_signature` (`count:hash` of each note's id and revision), not the notes, and the page fetches the list when it changes (`frontend/src/lib/notes/useTimelineNotes.ts`), and after its own writes when nothing polls. Every write that changes a listed note makes a new revision, so the signature changes whenever the list does.
- **Placement.** One rule, implemented twice: `place_timeline_notes` (`backend/utils/timeline_notes.py`) for prompts, and `placeTimelineNotes` (`frontend/src/lib/notes/placement.ts`) for the live and finished transcripts, both pinned by `backend/tests/fixtures/timeline_note_placement_cases.json`. A note at t (a selection at its last millisecond) follows the last non-blank line, in list order, starting at or before t. A note before the first line opens the transcript.
- **Views** place notes on their whole line list. A note after a hidden line shows after the visible line before it, and a note ends the run of grouped lines it follows. The views sort lines by start, while the prompts keep the stored order, which every writer emits by start: lines tied on start may sort either way without moving a note past a non-blank line (a property test in `placement.test.ts`). A list stored out of start order, which `PUT /transcripts/{id}/segments` accepts, would place a note differently in the views than in the prompts.
- **Highlights.** A selection's `quoted_text` is a snapshot of the words the user saw, and its `start_ms`/`end_ms` are where they were. The processed view finds them again at read time (memoised on lines and notes), never writing anything back (`frontend/src/lib/notes/resolveSelection.ts`). The rule: look only among the words timed within 2 s of the span, compare them case-folded with punctuation stripped, and take the run with the fewest word edits from the quote, ties to the run with fewer part-word matches, then to the run nearest the span's middle. A quote keeps just the characters selected, so it may start or end inside a word: its first word also matches the end of a word, its last word the start of one, and a one-word quote any part of one three letters long or more (so "a" is never found in "and"), with no edit counted. All words equal is *exact*; a score `1 − edits/quote words` of at least 0.5 is *fuzzy*; anything less is *unanchored*, and nothing is marked. A reprocess, a line edit or Find & Replace therefore never moves a note or its placement, which reads only the stored span, and the prompts keep the stored quote. Utterance ids and character offsets are never stored on a note, since a reprocess replaces both.
- **Prompts.** An anchored note is its own line after the line it follows, folded so it cannot pass for transcript. Head and tail notes go in `# User Notes Context`, quoted with `> `; chat puts them first and last. Speaker inference reads every note as a timestamped list. Generated notes end with `## User Notes`, which speaker renames never rewrite.
- **Meeting Edge** refreshes at once, ahead of its throttle, when `timeline_notes_signature` changes. It hashes each note's id and content (kind, text, anchors, quote, author, creation time), not its revision as the list signature does, so an edit that changes none of these refreshes nothing.
- **Revisions.** An edit names its base revision, and a delete may (`?expected_revision=`). A stale one is a 409 `revision_conflict` with the current note.
- **Write tokens.** A write may carry a client-chosen `write_token`, and the note reports the one that made its revision (`last_write_token`), so a client recognises its own write. An edit with a token always makes a new revision, fencing off an earlier write still in transit.
- **Tombstones.** A delete leaves a `timeline_note_tombstones` row with its token, so later writes to that id get a 410 (`note_deleted_by_you` or `note_deleted_elsewhere`) and a retried create never revives the note. A delete with a token of an unknown id leaves a `never_held` tombstone (kept an hour, at most 20 per recording), so a create whose answer was lost cannot outlive the user's clear. Client-id creates and deletes take `pg_advisory_xact_lock(hashtext(id))`. Backups omit tombstones, and a restored note whose id is tombstoned gets a fresh id.
- **Errors** carry `detail: {code, message}`. Clients branch on `code`, pinned by `backend/tests/fixtures/timeline_note_error_codes.json`. The note box's sync states are tabulated in `frontend/src/lib/notes/noteOutbox.ts`. The live box's outbox is one per recording for the life of the page, so notes on their way and the box's text outlive the live view. A note on a line from its ⋯ menu, in the live or the processed transcript, goes through the same outbox as a `selection` note quoting that line. So does a note on selected text, whose `start_ms`/`end_ms` are estimated: word times don't reach the client, so each word's time is interpolated by character offset across its line's span (`frontend/src/lib/notes/selectionRange.ts`), and the span covers every word the selection touches. Its `quoted_text` is the text as selected.
- **Unsaved notes in the browser.** Each outbox is also kept in IndexedDB (`nojoin-notes`), one record per account id and recording holding each unsaved note with its id and write token, the box's text and any discard whose delete is unconfirmed (`frontend/src/lib/notes/notePersistence.ts`). The id comes from `/users/me` and survives a rename. Once the session names the account, opening the recording again reads its record back and sends each note under the same id and token, so a create that landed before a reload returns its note rather than a second one, and a 409 or 410 is handled as on the first attempt; after a 409 the note goes out under its new id only once the record has it, or once a write under way has gone unanswered for 2 s (`NEW_ID_WAIT_MS`): a tab that closes or crashes before that write answers can leave the old id stored (a close no longer asks first, as the note has gone out), and since the server refuses that id again whatever the token, a reload makes a second copy of the note (it takes an id clash with another recording, a stalled store and the tab closing or crashing, together). A page writes only while its session is the account it read as, no sign-out has stopped storing, and no cleanup has removed that account's records since. Each `/users/me` drops every other account's records. The tab tells the others over a BroadcastChannel (`nojoin-notes`), as it does a sign-out, which stops every tab storing until a sign-in is accepted in it; a tab told of either repeats the removal for its own account, after any write it had begun, so a write that landed between the removal and the ping doesn't outlive it; without BroadcastChannel, other tabs go by their own sessions. Two tabs on one recording share the record, and the last to write wins. The record is therefore only a stopgap for a crash, a killed tab or an ended session: the leave warning (`noteOutboxes.ts`) is armed whenever anything is unsent, whatever is stored, and so is an edit or delete of a saved note from its Save or Delete until it is confirmed or its editor closes, a refused one still open included (`holdPendingNoteWrite`, in memory only, never retried; it holds sign-in in place too) (browsers that never show it, such as iOS Safari, have only the stored copy), and the sign-in dialog's way to the sign-in page goes through it. Records carry a `version`: an earlier version's record is upgraded one step at a time through `RECORD_MIGRATIONS` and left alone where a step is missing, a later version's is neither read nor written, and a note of a kind this version cannot send is written back unchanged. A new kind is therefore not a new version: `selection` notes add `startMs`, `endMs` and `quotedText` to their own stored notes only, and an older build keeps them as they are. A browser without IndexedDB, or one that refuses, keeps the outbox in memory only. While any outbox holds something unsaved, the page holds sign-in in place as a capture does (Session expiry, under [Browser Capture Stack](#browser-capture-stack)), so a device that only takes notes asks for the password instead of reloading to `/login`.
- **Unsent marks.** The recordings rail marks each recording with something unsaved in this browser (`useUnsentRecordings` in `frontend/src/lib/notes/useNoteOutbox.ts`). A recording this page holds an outbox for goes by that outbox; any other by whether the signed-in account has a record for it (`NoteStore.recordingsOf`), read when the page loads and again whenever this page's outboxes change, so another tab's writes show at the next read. Nothing is sent from the rail: opening the recording restores and sends as above, because a sender in the background would act on notes another tab may have open. Deleting a recording for good or discarding it here (`forgetRecordingNotes` in `noteOutboxes.ts`, called by the recording actions, the batch bar and a recording page that finds its recording gone for its owner) drops the page's outbox for it once any write of it under way has finished, removes the signed-in account's record, and tells the other tabs (`forgot` on the `nojoin-notes` channel), which drop their outbox for it and remove the record again. A record for a recording deleted on another device is never marked. Once per page load and account, when the rail's list first loads, `useForgetNotesOfDeletedRecordings` (`frontend/src/lib/notes/deletedRecordingNotes.ts`) checks the account's records whose recording is neither listed nor held by an outbox here, at most 20, two at a time, with `GET /recordings/{id}` (issue #636). A 404 `Recording not found` between two `/users/me` answers naming the record's account forgets it through `forgetRecordingNotes`, since under another account's session cookie the owner's recordings answer 404 too. Any other answer keeps it, a binned recording's 200 included; `backend/tests/test_recording_detail_after_delete.py` pins those answers.

#### Files On Notes

A note may hold one file (#653): a still of the shared screen, taken with the camera button or Alt+Shift+C, which makes a point note `Screen capture` at that moment, or a file pasted or dropped into the note box, which goes with the note being typed. It is a `documents` row with `note_id` (unique, `ON DELETE CASCADE` to `timeline_notes`) and `use_in_notes`, off by default (`backend/utils/note_attachments.py`, migration `c4d81e6a2f90`). Its time is its note's, so placement, ordering, moves, My notes and exports all come from the note.

- **Upload.** `POST /transcripts/{id}/timeline-notes/{note_id}/attachment` takes a file of any type through `store_upload` (`any_format`), with the documents' size limit, and stores the row `PENDING` with no parse. The file is stored under a fresh UUID and its own extension when that is plain letters and digits, else `.bin`, so a format becomes readable when the parser learns it, with nothing uploaded again. The title is the file's base name with control characters removed, and `file_type` comes from the extension, never the browser. A second file on a note is a 409, and a file for a note whose file was removed a 410. The client sends it once its note has saved: the outbox keeps the file in memory only, never in the IndexedDB record, and a failed upload waits with Retry and Discard on the note, or in the unsaved notes list after Stop; a 409, 404 or 410 on Retry means there is nothing left to send (`frontend/src/lib/notes/noteOutbox.ts`). A file pending upload holds the page and sign-in as an unsent note does. The browser takes a still from the share's video track (`CaptureController.displayVideoTrack`, never stopped, since ending it ends the share) through a detached video element, as PNG, or JPEG when the PNG would pass 4 MB (`frontend/src/lib/captures/frameImage.ts`). It reads the time when the user asks, before drawing.
- **The switch.** `PATCH .../attachment` with `use_in_notes` turns it, and refuses on (409) for a file the parser does not read (`is_readable`: an extension in `SUPPORTED_EXTENSIONS` and never SVG, HTML or XML). On, it queues `process_document_task` when the file has not been read (or failed), and either way it marks notes already written stale. A file switched off is never parsed: `process_document_task` returns before the parse, and the index rebuild skips it. `feeds_notes_clause` keeps files switched off out of `load_attached_documents`, and `unread_attachment_ids` keeps their chunks out of chat retrieval and `search_context`, so a file read while on and then switched off is not read again. A file switched on reaches the notes prompt with `note_at="MM:SS"` (`"meeting"` for a head or tail note) on its `<attached_document>` tag, with a paragraph telling the model to cite it by time and never embed it; a prompt without one is unchanged.
- **Reads.** A note's `attachment` comes with it in the notes list, with `readable`, and the list signature hashes each file's id, status and switch with the notes' ids and revisions, so a parse ending on a worker changes it. While a file switched on is being read, the recording page keeps polling the detail read (`noteFilesBeingRead`), whose signature brings the list again. The viewer reads notes through the page's edit overlay, so a note moved or edited there shows as it is. The documents list leaves note files out. `GET /documents/{id}/preview` draws a 640 px JPEG of a PNG or JPEG only, and refuses one past 64 megapixels. `GET /documents/{id}/download` always sends `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, and a type of its own: an image's for the viewer's picture, `application/octet-stream` for everything else, so no file renders in the app's origin.
- **Deletion.** Deleting the note deletes the row (pages and chunks cascade) and, once committed, the file. A recording's delete, discard and permanent delete remove note files with its other documents. Deleting a note whose file was switched on marks notes already written stale.
- **Removal (#734).** `DELETE .../attachment`, from the viewer's **Remove** after its confirm step, removes the file in one transaction that also decides the note's fate, under the note's delete locks (the id's advisory lock, then the row). A note whose text is still exactly what came with its file is deleted as its own delete would, tombstone and Meeting Edge refresh included, and the answer's `note` is null (`note_goes_with_its_file`): a point note reading `Screen capture`, or a note of any kind reading the file's title, which is what a file pasted or dropped with nothing typed gives it. No column marks either, so the text decides. The browser writes the file's name as the note's text, and the API trims it as it trims every note's text; the title is the same name with folders and control characters removed, trimmed and cut to 200 characters. The two are equal for an ordinary name, case and extension included. The comparison is exact, so a note whose name those steps changed, such as one past 200 characters, stays. Any other note stays as a text note with `timeline_notes.file_removed` set (migration `7bb9c74f9946`): the upload route refuses a file for it with 410, checked again under a share lock once the upload is stored, so an upload still on its way, such as a retry whose first attempt had landed, cannot bring the file back. The browser forgets any upload it holds for the note (`forgetUpload`) and fetches the list again; other viewers' polls see the list signature change. A file switched on marks notes already written stale, as turning it off does. Everything that read the file (notes, Meeting Chat, search, exports, MCP, the Captures tab) read its row, which is gone. `DELETE /documents/{id}` refuses a note's file (409), so this route is the only way to remove one.

### Imported Media Input

Import stores no video. Every import route (`/import`, chunked finalize, `/upload`) stores the upload as it arrived, marks the recording `QUEUED` with the step "Extracting audio..." and queues `keep_imported_audio_task` on the CPU lane ([backend/worker/tasks/imported_audio.py](../backend/worker/tasks/imported_audio.py)) in place of processing. The task runs `keep_imported_audio` ([backend/utils/import_audio.py](../backend/utils/import_audio.py)), points `audio_path` at the result, rebuilds the import's audio window, deletes the upload once that write has committed (a failed deletion is logged), then queues processing and the playback proxy.

- **Extraction.** For any media container, or any upload carrying video, the audio track ffmpeg selects by default is extracted into the recording's `temp/<id>/`. WAV, MP3, AAC and FLAC uploads are kept as they arrived without probing, so they need no ffmpeg.
- **Format.** AAC, ALAC, MP3, Opus, Vorbis and FLAC are stream-copied, PCM and other lossless codecs become FLAC, and anything else becomes Opus.
- **Verification.** The result is kept only if it is one audio stream no more than max(1 s, 0.1%) shorter than the source track, measured from packets.
- **Concurrency.** Each write is conditional on the recording still waiting with the same `audio_path`, and the upload survives until the kept audio is stored, so a duplicate or re-queued task is harmless. The extracted file moves beside the upload only after its write has matched the waiting row. That write takes the recording's audio lock before the row, the order discard takes them in, so a discard during it waits for its commit instead of deadlocking (issue #787). Tasks are acknowledged on receipt, so the CPU worker re-queues every waiting import when it starts (`requeue_imports_waiting_for_audio`). Delete, permanent delete, batch permanent delete and discard read the row `FOR UPDATE`, so they never delete a path the task has just replaced, and unlink the paths they read only once the delete has committed, so a failed commit keeps every file its row names. An ffmpeg left running by a killed worker writes only into `temp/<id>/`, which deleting the recording removes and the daily sweep clears.
- **Failures.** A bad file (no audio track, or one ffmpeg cannot extract) and a server fault (a missing tool, a timeout, a signal, a full disk) both mark the recording `ERROR` with the reason as its step and remove its files, upload included. Neither is retried, and reprocess refuses a failed recording with no audio, giving that reason.
- **Unfinished imports.** A chunked import sits in `UPLOADING`, with no client status, while its 10 MB parts arrive, and each part moves `last_activity_at`. Its page can close or lose its connection first, and then it stays there. The capture lock (`_get_active_capture_recording_for_user`) and the worker's check for a capture in flight, which keeps the live ASR model resident, count only live captures (`is_live_capture` and `live_capture_clause` in `backend/models/recording.py`: a client status of `RECORDING` or `PAUSED`, or the `PAUSED` status), so an import never blocks **Start Meeting** or holds the model (issue #569). The recording payload's `import_stalled` is true once no part has arrived for 15 minutes (`import_looks_stalled`), and the client offers such an import to import again or discard, after looking it up again (`UnfinishedImportNotice.tsx`). An import whose part fails is discarded by the page that sent it. One whose finalize fails is kept, because the finalize may have queued it before its answer was lost.

### Live Transcription Lane

While a recording is `UPLOADING`, `transcribe_segment_live_task` ([backend/processing/live_transcribe.py](../backend/processing/live_transcribe.py)) produces provisional text with the install's transcription engine.

- **Sequence gate.** Tasks for consecutive segments can run out of order. A per-recording `live-drain.lock` beside the `live/` directory uses the same filesystem `flock` mechanism as speaker labels, covering the checkpoint read, inference, carry promotion, failure recovery and checkpoint write on every worker sharing the capture storage. A busy task retries without changing audio or state, including when settling is off. The holder reads `next_expected` from `live/state.json` and drains the contiguous run from that chunk when present, including audio retained after a lifecycle rejection, so a task lost with a worker does not stall the lane. A missing head leaves later WAVs on disk until it arrives, or until five later chunks (about 10 s) are on disk: the lane then records the missing sequences as skipped (`gap_skipped`) and drains from the first chunk present. The skipped chunk takes no time on the live timeline, as in the master when a chunk is quarantined. One that arrives after being skipped is treated as already consumed, so the live lines after it stay early by its length until the final pass, which includes it, replaces them. Audio from an unfinished utterance is carried over in `live/buffer.wav` and joined to the next run, so an utterance split across segments is normally transcribed whole. Continuous speech is force-emitted after `live_forced_max_s` (8 s).
- **Regions.** VAD regions are padded (`live_speech_pad_ms`) and prefixed with a rolling context clip (`live/context.wav`, `live_context_window_s`) so word edges are not clipped; the output is sliced back to the region.
- **Writes.** The lane writes provisional canonical utterances, then refreshes `Transcript.segments` as a projection. The lane writes each utterance with speaker `UNKNOWN`; live speaker labels, when enabled, are written separately (below). The lane does record the capture channel: per-channel RMS decides whether the microphone or shared audio dominated, stored in `confidence_payload` and exposed on utterance reads as `source_channel` (`microphone`, `system`, or null when ambiguous). It identifies a channel only: a microphone-only capture reads as microphone for everyone in the room. Live utterance ids are a uuid5 of recording id, span, speaker and text.
- **Reads.** The recording view polls `GET /transcripts/{id}/utterances` every 3 s through capture, pause, upload, queueing and processing. While a capture is `UPLOADING` and live transcription is on, a read also carries `live_behind: true` once 20 s or more of uploaded audio sits in chunks at or past `next_expected` in `live/state.json` ([live_state.py](../backend/processing/live_state.py)). A state file caught mid-write reads as no lag. The lane writes that file only when a run ends, so the lag a read measures swings between about one and two runs' length, and the view clears its notice only once its reads have found the lane caught up for 20 s in a row, longer than the slowest run that can raise it (`LIVE_BEHIND_CLEAR_MS` in `useLiveTranscript.ts`). That outlasts the caught-up part of any run shorter than 20 s, so the notice holds steady rather than coming and going each run, and can stay about 20 s after the lane catches up. Provisional Analytics and Meeting Chat read the same canonical-first transcript with projection fallback through their dedicated paths; each labels its context as provisional. Detail metadata polling remains separate from the transcript feed.
- **Failures.** The lane is best-effort: a failed run is logged and the lane still advances. A failed run still accounts for the audio it drained. If it had carried audio into `live/buffer.wav`, the buffer is kept and `buffer_abs_start` moves to its start; otherwise `buffer_abs_start` moves past the audio the run read and the buffer and context clip are removed. Advancing `next_expected` alone would replay the stale buffer and stamp every later utterance early. The new state is saved in one write before any audio is removed.
- **Speaker labels.** With `live_speaker_labels=auto` and the GPU worker on CUDA, `run_live_speaker_labels` ([step.py](../backend/processing/live_diarization/step.py)) runs after text and ASR lane state are saved, in a separate failure boundary. Label failures do not fail live text or delay its cursor. The install-level `speaker_engine=auto|classic` defaults to `auto`, is administrator-managed and is resolved when a capture's labels first start. Master-off imports none of the label code; CPU-only hosts retain their current absence of live labels.
- **Audio and output timing.** In automatic mode, verified local Nemotron supplies labels while clustering runs alongside it. A separate sample cursor removes repeated ASR prefixes and retains partial packets. Both engines process the same chronological 32,000-sample packets; overlap matching and any switch to clustering finish before the next packet. Native windows keep their fixed settings and absolute 10 ms frame positions. Each output records when it became available as well as its prediction time, so a backlog cannot use a later re-cluster in an earlier switch. Missing assets keep clustering for the whole capture without requesting preparation. An eligible final pass requests preparation after the capture ends; a later eligible capture can use the model once preparation completes.
- **Line decisions and switching to clustering.** A native line takes the channel with greatest summed raw fp32 probability over available frames, lowest channel on ties. It stays provisional until its whole interval is available. Routing counts frames with float16 probability strictly above 0.5. When each of eight channels has accumulated 200 active frames, labels permanently switch to clustering at that output event. Native failure or an audio gap also causes a permanent switch; gaps do not insert silence into the native cache. Matching uses only native activity and clustering speech available by the switch, tracked by stable turn IDs through back-fill. Each current cluster takes the native channel with greatest overlap; multiple fragments may share a channel. New clusters and those with no overlap receive unused display numbers from 9 upwards. Clustering keeps classic's allocation, retirement and re-clustering, including reused numeric slots. Stable turn IDs detect slot reuse and give it a fresh display number. The saved state includes this continuity and mapping; display numbers are never reused, and locked lines keep theirs.
- **Classic labels.** Clustering uses segmentation-3.0 and WeSpeaker: a 5 s window every 0.5 s, short voices held pending, and re-clustering every 10 s. A turn locks after two unchanged passes or 10 minutes. Each pass considers up to 1,000 recent turns plus 10 older anchors per label. Lines need a strict majority of diarised speech, counting held speech against the winner. After switching, an unlocked line wholly covered by completed native output can finish from saved native probabilities; later-ending lines use mapped clustering decisions. Locked labels and manual assignments remain authoritative.
- **Label publication.** The canonical writer changes only provisional live utterances without a manual speaker lock. It locks Transcript first, then acquires lines in ID order with `FOR UPDATE SKIP LOCKED`, processing them separately in end-time order. A line held outside the fence remains open for the next run. The settled cursor assumes lines commit in end-time order; moving an open line's end behind that cursor leaves its old unlocked label until final processing. Each changed label increments the revision and appends a `live_speaker_label` event, then the projection's speaker fields are refreshed from all live provisional rows. The live panel periodically reads the whole transcript to recover changes behind its event cursor. Raw `LIVE_PROVISIONAL_<n>` labels remain separate from recording speakers: readers show “Speaker n” or its saved live name, and no `RecordingSpeaker` is created. Text, names and the existing final name carry-over remain separate from automatic identity translation.
- **Label restart and cleanup.** The versioned, atomic `live/speaker_labels.npz` stores clustering state, numeric native caches, pending audio, output probabilities, engine choice, speaker mapping and fingerprints, with `allow_pickle=False`. The append-only `speaker_labels.bank` is synced first, then the temporary snapshot, its rename and the directory. Decision state is saved before DB publication; settled progress and pruning follow, so retries reproduce decisions. Valid state resumes exact cursors and caches. Native failure switches to clustering if its identities remain intact; unusable identity state disables labels without changing text. A per-recording `flock` waits up to 10 s before skipping a busy run. Finalise deletes transient state; late queued runs perform no inference or label write. A run whose capture episode changed during inference (pause, resume or takeover) writes no labels; the next run labels those lines from its saved state. Final-pass eligibility is independent of live state.
- **Window manifests.** Each manifest has separate ASR and diarisation fields. The live lane writes ASR status (rows from older releases can also read `catch_up_processed`). Nothing writes diarisation status any more, so new windows stay `pending`. The legacy `status` field is a compatibility projection; new logic should read the lane fields.

At finalise, `process_recording_task` transcribes the whole recording again. Ordinary whole-line recordings retain their existing reconciliation: live text and automatic live speaker labels are not reused, while matching manually locked text and speakers remain. Settled recordings additionally preserve accepted human wording, split boundaries and assignments when final boundaries drift ([Live Word Settling](#live-word-settling)); retained protected lines may therefore keep their earlier labels. If the final pass fails, the previous lines stay as the recording's transcript until a successful retry replaces them. Live labels still show as "Speaker <n>" or their saved live name, and editing one makes no `RecordingSpeaker` of a live label. Superseded rows retain their labels and text in the database, but readers return only active rows. Finalising the capture deletes the label state, as does a finalise whose master cannot be built (before the segments move to `failed/`), and a label step still running then writes nothing and removes what it saved. Deleting or discarding the recording removes its whole temp directory, and storage hygiene never lists files under `temp/`.

### Transcript Publication Fence

Live text, live labels and naming, canonical append/replacement/finalisation, human edits and lock release all acquire the recording's Transcript row before reading publication state. Affected utterance rows are locked in ascending database ID order. The first fence acquisition refreshes clean cached fields after waiting; re-entering it preserves this transaction's pending changes. Live publishers neither lock nor update Recording. ASR, alignment, diarisation and embedding inference run outside these publication transactions.

Pause, resume, finalise and discard use the order **capture audio advisory lock → Transcript → Recording**, with a Recording row lock where deletion requires it. Publishers hold Transcript only for their short database publication, never during inference, so a lifecycle control waiting for it holds uploads back only briefly. Uploads retain their existing audio bookkeeping and throttled Recording activity update, with no Transcript fence. A publisher snapshots the capture epoch and, for marked captures, generation before inference, then checks current eligibility and that token after acquiring the fence. Resume changes the marked generation; stop seals it. Rejected results advance neither the live checkpoint nor the label step. Naming checks fresh eligibility under the same fence.

Stop seals the live episode under Transcript right after its epoch check, before it rebuilds the chunk and window rows that publishers also update, and holds both locks until it commits. Text edits made during Stop wait for that commit. Discard revocation and artefact cleanup follow its database commit.

Deleting a recording takes Discard's order too: the audio lock, Transcript, then Recording (`lock_recording_for_delete`), since a live capture's publisher holds Transcript before Recording and the audio bookkeeping takes the audio lock first. Permanent and batch delete locked the row first and reached Transcript only through the cascade, which could deadlock with either (issue #816). A batch takes each recording's three in id order and skips one another request deleted while it waited. An **Overwrite** restore takes them batch by batch before its pre-delete, and reprocess locks Transcript before it writes a changed speaker cap or language to the row. Polling is the only read path: live views poll utterance deltas with the existing event cursor (`after_revision`) and a periodic full read.

`Transcript.change_sequence` (BIGINT, exposed read-only with the transcript) tells a finished view that something it shows has changed. Writers advance it explicitly through `change_sequence_bump` (`backend/utils/transcript_change.py`) in their own transaction: the shared projection refresh (split, speaker identity and merge, finalise, reprocess), text and speaker edits, lock release, compatibility replacement, a retained reprocess's publication (which may write no lines), unmerge, a settling pass that changes lines, speaker colour, speaker delete, merge and split, voiceprint-dialog and People-scan links, regenerated notes, notes edits (including find-and-replace and the chat tool), finished speaker inference and automatic meeting intelligence, the edits made with canonical writes off, and a person rename for every linked recording. It is a hint, not a cursor: `after_revision`, line revisions, tombstones and the analytics watermark stay on the utterance events, and a writer that does not advance it leaves a finished view stale until it reloads. `GET /recordings/{id}` sends a weak ETag of the status, the counter and the notes status with `Cache-Control: no-store`. A finished view re-checks every 15 s with `If-None-Match`; the answer is a 304, read without loading the recording, until one of them moves, so notes generation started elsewhere also brings back the regular poll. Then it takes the full recording, and the full transcript when the counter moved; the new ETag is kept only once that transcript read has succeeded.

Full reprocess and retry reset the Transcript row in place: generated fields return to their defaults while its identity and change counter are kept, and the reset advances the counter. Recordings with literal `settled: true` additionally retain their current canonical lines, projection, speakers and human naming acts until successful final publication.

Nullable `Transcript.settling_state` holds a new-capture eligibility marker, confirmed CPU/CUDA enablement, source generation UUID, capture epoch, phase and seal flag, alongside any durable resume boundaries. `live_text_settling=auto` (GPU only) or `always` (GPU and CPU) marks new captures; `auto` is the shipped default, with K=3 and a 10 s window. Missing installation values inherit these defaults; a stored `off` remains off, including values saved as defaults by earlier versions, which carry no choice provenance. The canonical-write rollback setting prevents settling for new or resumed episodes. Under `auto`, explicit CPU or unavailable CUDA prevents rolling decoding; `always` decodes on the CPU too, read at each step. Actual placement comes from the loaded Whisper model's device or ONNX sessions' active providers. An unloaded engine can make one speech-gated observation to establish placement. A silent first chunk loads no model. K and the window are read at each step, so a change applies from the next one. The mode is taken when an episode starts. Pause closes that episode and resume starts a new generation. A capture created under `off` has no eligibility marker, so a later resume cannot enable settling. Unmarked recordings and captures retain whole-line behaviour.

### Live Word Settling

Marked captures with settling enabled (confirmed CUDA, or the CPU under `always`) use a rolling pass per received **2 s chunk step**. When the lane drains a backlog it decodes only the latest step; older passes are dropped rather than queued and contribute no comparisons. The audio input is capped at **10 s total** by default, including up to **5 s** of lead-up (`live_context_window_s`, bounded by the total cap). The worker selects the earliest unlocked word minus that lead-up, constrained by the window edge. It retains no meeting-sized word history in its runtime state.

The speech gate is **VAD OR available diariser speech** anywhere in the unlocked window, after excluding muted PCM: from the newest of the window edge, the available audio and the locked frontier to the end of the captured audio. VAD covers the newly drained chunks; diariser speech covers the whole window, so after a turn the following silent steps keep decoding while its words are unlocked, and they lock by agreement instead of waiting for expiry. Diariser speech that VAD missed opens the gate while it is still in the window, but the decode start stays the one planned from the unlocked words; the final pass recovers speech it leaves out. When a backlog drains, speech still inside the window shares the one decode at the latest step, even when the newest chunk is silent. Diariser evidence that arrives after its audio has left the window cannot reopen it.

The worker reads only already available speaker evidence and never waits for a new diariser pass before ASR; label processing can advance independently of whether ASR succeeds. This allows the bundled single-slot GPU worker's later diariser evidence to rescue ordinary VAD misses without GPU concurrency changes. Skipped or failed decoding adds no word comparison. Speaker labels being off does not disable text settling.

The existing `confidence_payload.asr_segments[].words[]` carries stable UUIDs and order, exact text spans, absolute native or forced-aligned timings, lexical comparison signatures, unchanged-comparison counts, accepted decode identity and locks. Whisper and Parakeet keep their native word timings; Canary uses the CPU forced aligner on the same rolling window. Untimed words retain null timings and move with their timed neighbour, following the aligner's existing grouping. If alignment fails for a whole hypothesis, overlapping locked context is removed at a lexical boundary before its exact suffix is published as an untimed atom; a decode starting beyond the locked frontier retains repeated wording. Repetition filtering removes matching text and word evidence together.

**K=3 means four observations**: the initial appearance has count zero, followed by three unchanged successful comparisons. Monotone lexical matching requires compatible word centres within one second. Punctuation and case changes update unlocked exact wording without resetting lexical agreement. Changed words reset their count; retries, failures and dropped/skipped passes do not count. Only an agreeing prefix locks, so an unstable earlier word holds back a later stable word. Locked word dictionaries are immutable to subsequent machine passes. Words reaching the total-window edge lock **as-is** with reason `expiry`; prefix agreement uses `agreement`. Stop, pause and finalise lock the last successful hypothesis with reason `closure`, without another decode. The segment the browser uploads as it pauses still decodes while paused; once that live task's speaker labels have run, its words and speakers lock with reason `closure`, unless a Resume has started a new episode since.

The projector groups words into one speaker's continuous line, using each word's majority-overlap label decision. A speaker change, an inter-word gap strictly greater than `line_break_pause_s` (1 s by default), a retained closure/barrier, or the legacy `live_max_segment_s` limit (30 s by default, split between words) ends a run. Final word-level grouping uses the same pause helper and float tolerance. The recording owner's resolved pause (0.5–5 s) is read during processing and retained for speaker-only reprojection; stored transcripts are not rewritten when settings change. VAD/decode retain their separate `LIVE_MIN_SILENCE_MS` (320 ms) threshold and 8 s forced-decode trigger. Chunk boundaries, decode steps and changes in word lock state never split a line. Available VAD and diariser evidence can confirm trailing silence longer than the line pause; a short ASR hypothesis alone cannot. Accepted silence bounds carry across contiguous chunks, reset on later speech or missing coverage, and clear with a new capture episode or CPU fallback. Untimed atoms conservatively use their actual observed audio end. Pause, Stop and finalise close the remaining open line.

New words extend the open run even when its earlier words have locked or left the audio window. The projector keeps that row in the affected tail until it closes. It preserves exact word dictionaries and identities, and retains individual settled speaker locks when newly appended words still have pending speaker evidence. A tentative speaker boundary cannot freeze its left line until the next word and its speaker settle, so a pending unknown tail can rejoin the same speaker. A confirmed line end stays on the line's last word when a revision only retimes it. When a revision retokenises or replaces that word, or recovers speech after it but before the confirmed end, the capture time is kept instead, and a later word starting at or after it begins a new line. Untimed alignment-failure atoms retain null word times and use their actual observed capture bounds for line limits and pause closure. Equal memberships update in place; changed memberships use the existing atomic replacement and tombstone path under Transcript, retaining superseded snapshots. Text and speaker locks are independent. A line becomes effectively locked only after closure, stable boundary evidence, and locks on all its words and speaker; later live machine work cannot alter its ID, wording, speaker, bounds or membership. Existing manual text and speaker protection remains authoritative.

Inference and alignment run outside publication transactions. Each result carries epoch/generation and a deterministic chunk-step decode ID. After the fence, stale, sealed, duplicate or reordered work is rejected before comparisons change; work for a paused episode publishes, and its task closes the episode again after its labels. Lock-only changes also emit line events. Public reads expose typed `words`, `text_locked` and `locked`, excluding private comparison evidence.

Live speaker decisions distinguish coverage from stability. Optional public `diarisation_pending` marks live lines whose time range has not yet been fully processed by the selected diariser route; their stored speaker remains `UNKNOWN`. Classic timeline coverage and native posterior coverage supply this fact independently of speaker locks, through both accepted-checkpoint reads and direct label publication. Covered but unassigned `UNKNOWN` remains a separate line even while its evidence is unstable. The flag lives in the existing private speaker payload, and canonical partitions split when pending state changes. Closure (Pause, Stop, a takeover resume or the CPU disable) clears pending and locks those words with the speaker of the nearest earlier decided word from the same audio source (the source badge their line would show), counting the last line already locked before them; they stay `UNKNOWN` only when nothing from that source precedes them. The final pass corrects a wrong guess. Processed transcripts never carry the flag. The frontend mirrors the public flag on segments and utterances and composes pending fragments inside the preceding same-source bubble for display, retaining each fragment's word identities, revision, timing and note/selection targets. A first pending fragment uses neutral styling.

Rejected lifecycle work retains its lane checkpoint and accepted carry audio. A later upload wakes the lane from its earliest unconsumed chunk whenever that chunk is present, so Resume can drain the retained audio without retrying the exact rejected task. A genuinely missing chunk holds the lane until it arrives or five later chunks are waiting (see the sequence gate above).

During settling, canonical rows are the live authority: only affected line JSON and bounded episode metadata are written per step. The growing `Transcript.segments`/text compatibility snapshot is coalesced until lifecycle closure, when it is rebuilt with word/protection evidence. Live readers use canonical utterances, including transcript detail/download, MCP, Meeting Edge, notes eligibility and speaker samples. Full and incremental utterance reads expose typed word identities and lock fields only for marked lines; legacy responses keep their existing fields. An empty canonical result clears the live read rather than reviving old snapshot text. Keyword search joins canonical line text in transcript order, preserving matches across line boundaries. Explicit user mutations can materialise the compatibility snapshot under the existing fence before resolving segment indices; decoder steps never do so. Marked captures share time-based line ordering across rolling, CPU fallback and compatibility writes.

Public `settling_required` reflects literal settled provenance or an eligible capture's confirmed enabled policy, never current installation settings. The client offers text edits, speaker assignment, splits and line notes only on locked lines, and a selection note only over locked words, since a settling word's wording, time and speaker can still change. The server refuses only a split on a line still settling (409), judged from the same public `locked` field; each edit sets the line's existing manual text or speaker lock, which keeps it an immutable anchor for later settling passes. A speaker assignment for the whole transcript also reaches that speaker's lines still settling; those are marked line-locked, so they read as locked instead of settling until the final pass. Live naming keeps upstream's anchor rule: the label's longest locked turn, or its longest turn when none is locked or the locked one is under a second. Splits supersede the source with two children retaining genuine word UUIDs and durable split-group/boundary provenance. Human replacement text is a single untimed atom. A growing open line with a unique corresponding word run keeps its UUID and emits an update; true splits and merges retain supersession events.

Final processing still transcribes the complete recording. The first publication of settling words sets a durable `settled: true` bit in `Transcript.settling_state` under the same fence. Recordings with that literal provenance stage final ASR output through speaker assignment; completion metadata, canonical reconciliation and the compatibility view then publish together before notes generation. A failed reconciliation rolls back the settled view; before publication, terminal pipeline errors on this lane cannot be reset to PROCESSING by stale component state. After publication, notes-context, enqueue and inline notes failures retain the final transcript and follow the ordinary lane's component statuses, error messages and status recomputation; timeouts and cancellation retain its interruption handling. An enqueue failure therefore leaves the notes `generating` until their claim expires ([Runs Lost With A Worker](#runs-lost-with-a-worker)); the recording itself completes. First-time unmarked recordings retain their existing publication timing and component-status recomputation: completed ASR text is visible before speaker assignment and survives a later speaker-stage failure. Optional indexing and analytics dispatch failures do not change a completed recording's status on either lane. The no-speech shortcut reconciles an empty result on the settled lane as well.

Reprocessing a completed ordinary recording uses an independent literal `reprocess_pending: true` marker in the existing transcript state. A completed empty transcript counts as a previous publication. Requeue retains the published transcript, speakers, notes and their template provenance, title, suggestions and Meeting Edge payload, history and user focus. A failed transcription keeps it and its `error` status, so the recording reports the failure over the retained transcript and a later retry retains it again; any other failed pass, a time limit or a stopped task included, clears it and hands the retained transcript back as completed, since nothing retries an interrupted pass and a later Retry retains the transcript again. While the replacement runs, notes generation (including MCP's), speaker inference, and transcript and per-recording speaker edits (including the MCP correction and naming tools) answer 409, since publication deletes the retained lines, speakers and their edit history. It never enables settled-only edit guards or human-text preservation. Publication clears it and sets `reprocess_published: true`, so the new result remains readable while optional notes still run; the recording reaching PROCESSED or ERROR, or the task being stopped, clears that too. Detail responses expose `previous_publication_available` for the pending replacement and `reprocess_publication_complete` for its completed publication, including on reload during notes generation. Like any in-flight detail response, these carry no transcript text or segments, which the view would otherwise receive on every poll; it reads the retained and the new publication from the utterances endpoint, showing a loading message until the first read lands. The recording view keeps the publication read-only while processing and replaces it only after a successful snapshot of the new publication arrives.

For this ordinary reprocess lane, speaker resolution starts fresh: retained labels, manual merges, names and embeddings cannot identify the new clusters. Old processing, canonical, naming and correction state, speaker name suggestions, chat and transcript context chunks are removed only within the successful publication transaction. The replacement transcript, speakers, canonical rows, projection and global voiceprint learning/drift changes commit together, before optional notes generation. With canonical writes disabled the old canonical rows are removed and the replacement projection is written directly; empty/no-speech success follows the same boundary. Failure before that commit retains the entire previous result and leaves the recording in `ERROR`; failure afterwards retains the new transcript. Notes, title and Meeting Edge keep their previous values until their individual regeneration replaces them, so a notes failure cannot roll back a successful transcript. Settled recordings retain their separate reconciliation and reset contract.

For settled recordings, accepted text and split boundaries survive. A speaker-only correction protects the speaker, not the text: the final wording replaces the line, and the manual speaker passes to the final segments that overlap it. Exact remaps preserve protected word evidence, and a final wording that differs from the kept text is exposed as typed `final_review` on that line. Otherwise a final segment that directly overlaps a protected line is split at its word timings: the words whose midpoint lies in a protected line are exposed once as typed `final_review` on that line, and runs of its other words take the ordinary final path, speaker assignment and manual speaker inheritance included. Runs split at every protected line between their words, even one holding no word's midpoint, and each run's bounds stop at the edges of the protected lines beside it, so a word straddling a line's edge keeps its own timing without carrying that line's manual speaker into the run, on either side. An untimed word goes with its timed neighbour, as everywhere else in the pipeline, and only a segment with no timed word is exposed whole on the first protected line it overlaps. Final segments that overlap no protected line, and every unprotected line, take the ordinary final path, so one correction never holds back its neighbours. This avoids duplicated paragraphs and guessed timings for replacement text. Empty success retains protected lines and retires other output. Unprotected authoritative final evidence replaces live words and clears obsolete settling/speaker locks; wordless output clears stale timings even when wording is unchanged. Public final reads derive repeatable word UUIDs from the line identity and its existing timed evidence, without changing stored ASR dictionaries. Split validation derives the same identities, so the finished-line menu can split at a real word. The existing typed `words` contract exposes these fixed words without restoring live line-lock fields or comparison evidence; protected children retain the chosen word identities. Native Whisper/Parakeet and forced Canary timings share this contract. Recordings that never published settling words retain the existing final evidence behaviour, including Auto captures resolved off on CPU. Episode changes and generated-state resets preserve the durable bit after line metadata is removed.

Backup format remains **3**, with the same table registry and canonical-table exclusions. A live export renders canonical words and private protection evidence into the archive's transcript rows inside its existing repeatable-read transaction, without writing the database compatibility snapshot. Protected text atoms, manual flags, split boundaries and word UUIDs live in archived segments; selection quotes and time anchors remain in timeline notes. Standing human naming acts are copied to durable `settling_state.name_anchors`, independent of excluded audit tables. Restore remaps person links and rebuilds naming acts by stable public identity, resets the change counter to zero and discards runtime metadata while retaining literal `settled: true` and those anchors. Archived segments rebuild canonical rows; a safe merge retains an existing target transcript unchanged. Interrupted captures retain the existing deliberate-reprocessing policy.

### Meeting Edge

After new live segments land, `refresh_meeting_edge_task` is dispatched best-effort: a failed dispatch is logged and the triggering request still succeeds. The task sends the provider a bounded recent transcript window, the previous run's rolling summary (a model-maintained 150 to 300 word running context), the previous suggestions so still-relevant ones are kept, the user's notes and focus text, and linked calendar context, and asks for strict JSON. Gemini (`response_mime_type`), OpenAI (`response_format`, retried without it for incompatible endpoints) and Ollama (`format: json`) use native JSON modes; Anthropic relies on the prompt. A tolerant parser accepts fenced or inline JSON from any of them. Changing the context-level slider or the enable toggle also refreshes the user's in-flight recordings, and the context level is part of the refresh signature.

Meeting Edge uses the configured provider's live model when one is set, else its main model.

A Redis single-flight guard (`backend/core/single_flight.py`) admits one refresh per recording at a time. Surplus triggers are dropped, since the next carries fresher transcript, and recorded as `meeting_edge_refresh_skipped`. The guard is a key with a TTL, so a worker killed mid-refresh releases it on expiry, and it fails open when Redis is unreachable.

### Utterance Public Ids

`transcript_utterances.public_id` is unique across all recordings. A segment's `id` is only a request, because openai-whisper numbers its segments in the same field. The merge keeps only string ids, so those numbers reach finalise only through the fallback that skips the merge, and backfill only through older projections. Finalise and backfill (`replace_utterances_from_segments`) take ids from `UtterancePublicIds` in [backend/utils/canonical_pipeline/public_ids.py](../backend/utils/canonical_pipeline/public_ids.py): an id no utterance holds is kept (finalise also requires a canonical UUID); one this recording already holds is replaced by a fresh uuid4 and recorded in the new row's `confidence_payload.source_public_ids`; anything else gets a uuid4. The bulk segment edit's full-replace fallback keeps the client's ids and answers 409 when one is held or repeated.

### Startup Canonical Cutover

`backend/entrypoint.sh` runs Alembic (`backend.startup_migrations`) and then `backend.startup_canonical_cutover` before the API starts. The cutover takes a database advisory lock and classifies every recording whose `pipeline_generation` is unset:

- `legacy_backfilled`: canonicalised, and viewable through the compatibility projection.
- `legacy_reprocess_required`: in flight during the upgrade, or not safely convertible. It must be reprocessed before transcript or speaker edits.

Recordings created or rebuilt by the current pipeline are `unified`, the only state with full edit support. Operator switches for the cutover are in [DEPLOYMENT.md](DEPLOYMENT.md).

## Stall Detection

A stall during live capture loses audio: the browser keeps counting time while nothing reaches the server. The API runs a watchdog on its event loop (`backend/utils/stall_watchdog.py`) that reports two things:

- **Event-loop lag**, the overshoot on a fixed sleep, as an `event_loop_stalled` pipeline metric when it exceeds the threshold. A blocked event loop, a throttled cgroup and a host paging the process out all show here.
- **Pressure Stall Information**, read from `/proc/pressure` when lag is detected, names the cause, since PSI's `avg10` window still reflects a stall that has just ended. It is absent on non-Linux hosts and kernels without PSI, where lag is reported without a cause. Sustained high pressure without a stall is reported as `host_pressure_high`, rate-limited.

Nothing is logged on a schedule. Settings are in [DEPLOYMENT.md](DEPLOYMENT.md#stall-detection).

## Anonymous Telemetry

Two Celery Beat tasks on the IO lane report to the collector under a random install id held in `data/.install_id`, with no meeting content, names or addresses. What is sent and how to turn it off are in [TELEMETRY.md](TELEMETRY.md).

- `send_telemetry_heartbeat_task` checks every 15 minutes and sends the install id and version when the install has never sent one, has started on a new version, or has not sent one this UTC day.
- `send_telemetry_ping_task` sends the usage diagnostics every six hours once the install consents. The collector upserts on install id and UTC day.

Each value has one writer: the API writes the `telemetry_*` keys in `config.json`, the worker writes the Redis send markers, and the install id file is write-once. Sending is best-effort: the diagnostics never retry and a failed heartbeat waits an hour. The collector, a Cloudflare Worker with a D1 database, is in [telemetry/](../telemetry/).

## Calendar Flow

Setup and sync behaviour are in [CALENDAR.md](CALENDAR.md).

- Synced events, with descriptions and attendees, are stored in `calendar_events` under `calendar_connections` and `calendar_sources`. The dashboard combines them with recordings not linked to an event.
- `sync_calendar_connections_task` runs on the IO lane every 15 minutes, incremental through each provider's change cursor (Google `syncToken`, Microsoft Graph `delta`). With live sync on and a public HTTPS origin, Google `events.watch` channels and Graph subscriptions (`calendar_push_channels`) trigger an immediate incremental sync by webhook.
- A sync that cannot be incremental (the monthly shift of the 25-month window, a missing or reset cursor, or the Microsoft partial-occurrence repair) fetches the whole window and reconciles it by `provider_event_id`, updating events in place. Events the listing omits are deleted, except those that ended before the window and are linked to a recording.
- `recordings.calendar_event_id` is nullable and `ON DELETE SET NULL`. Processing links a recording to a confidently overlapping event, or the user links one by hand. A linked event feeds the notes and speaker prompts and replaces the recording's own item on the dashboard calendar.

## Storage and Persistence

- **PostgreSQL** with pgvector holds metadata, transcripts, speakers, embeddings and settings. Migrations are Alembic, in `backend/alembic/`.
- **Redis** is the Celery broker and result backend and holds short-lived guards and send markers.
- **`./data`**, mounted at `/app/data`, holds `config.json` (install-wide settings), `recordings/`, `documents/`, logs and the install id.
- **Recordings.** Uploads use `recordings_root_dir()` (`RECORDINGS_DIR` or working-directory-relative `data/recordings`); restores and the demo seed use `PathManager().recordings_directory`, which follows `NOJOIN_DATA_DIR`. Ordinary deletion accepts either root through `stored_paths.recording_roots()`, with symlinks and `..` resolved before checking containment. Restore overwrite deletion stays confined to its explicit recordings directory.
- **Secrets.** Calendar OAuth client secrets and tokens, push-channel secrets and CLI OAuth credentials are encrypted with `DATA_ENCRYPTION_KEY` (`backend/core/encryption.py`).
- **Backups** are built by `create_backup_task` on the CPU lane and restored by `restore_backup_task` on the IO lane (`backend/core/backup/`); see [BACKUP_RESTORE.md](BACKUP_RESTORE.md).

### Storage Hygiene

`backend/utils/storage_hygiene.py` finds the document, audio, proxy and partial-upload files that no row names, with the listing and the reference read in `storage_hygiene_scan.py` and the circuit breaker in `storage_hygiene_breaker.py`. The daily `cleanup_temp_recordings` runs it last, and `python -m backend.storage_hygiene` runs it on demand ([DEPLOYMENT.md](DEPLOYMENT.md#storage-hygiene)).

- **Flag by default.** The daily run removes nothing unless `NOJOIN_STORAGE_HYGIENE` is `delete`, and the CLI nothing without `--delete`. Rows whose file is missing are reported and never changed. An exception in a run is logged and never fails the daily cleanup.
- **Listing, then rows.** A run lists the documents directory and both recordings roots, `recordings_root_dir()` and `PathManager().recordings_directory`, resolved and each once, before it reads `audio_path`, `proxy_path` and `documents.file_path` in one statement, soft-deleted rows and documents without a recording included. A file written after the listing is never a candidate. The rows are read again before the first unlink, so a row committed before then keeps its file.
- **Keys.** A listed file is referenced when any of its keys matches a row's: its device and inode, as `document_file_identity` gives them; its file name, compared without case, so a stored path that resolves elsewhere still keeps the file; and, for a recording that is `UPLOADING` or `PAUSED`, its name up to the first dot, which keeps the `.flac` master and its `.part` that finalize writes beside the `.wav` the row names. Keys only ever keep more files.
- **Names.** Only names Nojoin writes are candidates: `<uuid4>[.restored][.ext]`, `<name>__<uuid4>[.ext]`, `demo_welcome_<id>[.ext]`, and the `.part`, `.<32 hex>.upload-tmp` or `.<8 hex>.tmp` of one of those. Any other file is reported as unrecognised and never removed. An unreferenced `.mp3` is a proxy when a file of its base name sits beside it, and audio otherwise.
- **Grace.** Nothing modified in the last 24 hours is removed, which covers a file whose row has not committed yet. Each file's inode and mtime are checked again right before its unlink.
- **Scope.** Only regular files directly inside each directory. `temp/` and `failed/` belong to the existing 24-hour sweep, and dotfiles and symlinks are left alone.
- **Circuit breaker.** Any rule makes a run report only:
  - an empty `recordings` table while the directories hold files;
  - a directory that is the data directory, contains it, or holds `config.json`;
  - more than half of one column's stored paths naming missing files, leaving out recordings that are pending, in error or cancelled, which can lack their file by design;
  - more than half of the stored paths relative to the working directory naming missing files;
  - more than half of a directory's recognised files past the grace unreferenced, which no option lifts, logged at ERROR when the run would remove files and at WARNING otherwise;
  - removing more than 10% of a directory's files or bytes, which `--allow-bulk <directory> --expect <count>`, given once per directory, lifts for that directory when the count is the dry run's;
  - the restore lock held or unreadable. It is read before the listing, before the first unlink and again every 25 flagged files, and fails closed, because a restore proceeds without it when Redis is down. Its 6-hour expiry bounds what it covers;
  - in a deleting run that every other rule lets through, a directory with candidates whose clock trails the worker's by more than an hour, logged at ERROR. The grace compares mtimes with the worker's clock, but an NFS server stamps mtimes itself (nfs(5), "File timestamp maintenance") and the Linux cifs client may write its own back on close. The restore lock is read again, then the run creates `.nojoin-hygiene-clock` with `O_EXCL` in each directory it would remove files from, writes and fsyncs it so it is stamped as Nojoin's own files are, reads its mtime back from the filesystem and removes it in a `finally`. The lag is measured from the later of the grace's start and the current time, so a worker clock stepped back mid-run cannot hide a bad cutoff. On `ENOSPC` or `EDQUOT` the empty probe's creation stamp stands in, which can only show as much lag or more. A probe that cannot be created trips the rule, which fails closed, and so does one already there: a run never writes or removes a file it did not create, and a probe it could not remove stops the next run rather than piling up. The name is a dotfile, so no listing, concurrent ones included, sees it. A directory with no candidates is not probed, since a lagging clock only makes files look older; one that had candidates and is gone trips. A report-only run, or one another rule stops (a restore included), writes nothing, and a clock running ahead only keeps more files, so it needs no rule.
- **Audit.** Every removed file is logged at INFO with its size, mtime and category, and a trip at WARNING with its rules, or at ERROR where noted above. A run that removes nothing lists its candidates, the daily run up to 50.

## Release Model

A `vX.Y.Z` tag releases the API, worker, worker-io and frontend images to GHCR together, and the app reads release metadata from GitHub Releases. [scripts/release.py](../scripts/release.py) builds, scans and smoke-tests the images on the maintainer's release host and pushes them before the git tag. [release.yml](../.github/workflows/release.yml) then verifies and signs each image and only after that moves the rolling `major.minor` and `latest` tags, so a failed release never reaches `latest`. Anyone editing CI, the release workflow, the script or the Dockerfiles must keep that ordering, the SHA and digest pinning, and the signing identity. The full process is in [DEVELOPMENT.md](DEVELOPMENT.md#release-workflow-and-version-detection), and image verification for operators in [DEPLOYMENT.md](DEPLOYMENT.md#verifying-an-image-before-deploying).
